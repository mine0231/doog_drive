# doog_drive

基于 **STM32G474** 的 **FOC 关节电机驱动器固件**。每块驱动板驱动一台带减速器的无刷电机，
接收上位机（RK3588S）通过 **CAN** 下发的控制指令，支持开环 / 闭环速度 / 闭环位置 / 转矩 /
对齐等多种运行模式，并内置完整的软件保护与故障自恢复机制。

## 项目总览

### 目标应用

四足机器人关节驱动：上位机 RK3588S 带两路 FDCAN，每路挂 6 个关节电机（单侧前后两腿 × 每腿 3 关节），
共 **12 个节点**。所有驱动板硬件完全相同，只有 `NODE_ID` 宏不同，分别编译烧录 1~12 号固件。

### 主要功能

| 功能 | 说明 |
|---|---|
| **FOC 矢量控制** | Clark / Park 变换 + 七段式 SVPWM，电流环 **20kHz**（TIM1 更新中断，RCR=1 单采样单更新，`control_dt = 50µs`） |
| **多模式运行** | IDLE / 开环 / 闭环速度 / 闭环位置 / 转矩 / **对齐**（两步磁力定位，由指令触发，自动求零点偏移与方向；**上电不再自动对齐**） |
| **闭环级联** | 位置环 → 速度环 → 电流环（d/q 双轴）三级级联，位置式 PID（微分先行 + clamping 抗积分饱和） |
| **开环「转角度 + 悬停」** | 按开环方式转到减速器输出端指定角度，到位后进入"电弹簧"悬停保持（`RUN → HOLD → PULL` 子状态机） |
| **缓启动** | 速度斜坡（80 rad/s²）+ 开环 V/f 带低速升压，防止上电冲击 |
| **CAN 总线控制** | FDCAN2 @ **1Mbps**，命令帧 / 状态反馈帧 / 开环动作状态帧 / **故障详情帧**，多节点 ID 编址，总线错误与 BusOff 自恢复 |
| **串口调试** | USART3 @ **115200**，发送非阻塞（2KB 环形缓冲 + DMA）；命令行支持在线查看状态、修改模式 / 速度 / 电压 / 转矩、在线调 PID、CAN 诊断、故障读取；`v=` 设非零电压后 **3s 自动归零**（`AUTO_STOP_MS`），`log=1` 每 **200ms** 周期上报 |
| **软件保护** | 堵转、编码器失效、通讯失联、过温、母线过压 / 欠压、超速、相电流峰值、I²t 热积累、位置跟随误差、软限位共 11 项，另有 DRV8353 硬件故障（nFAULT） |
| **故障恢复** | 指数退避（2s→4s→8s→16s 封顶）+ 条件复检，恢复后由中断统一切回 **IDLE**（清目标 / 电压，重新走斜坡缓启动，不直接回开环）；阻塞式驱动恢复放在主循环执行 |
| **编码器同拍采样** | KTH7823 在 **TIM1 20kHz 中断内**每拍读 1 帧 SPI（16bit ≈1.78µs），多圈解包裹后按实测角速度外推补偿 1 拍延迟；1kHz 慢路径（sin/cos 低通 + atan2，≈7µs）留在主循环，**SPI1 单一所有者** |
| **可观测性** | `DBG_Monitor_t dbg` 调试快照（实现在 `foc.c`；**当前 `main.c` 主循环中的 `DBG_Monitor_Update()` 被注释，`dbg` 不会刷新**，需要时手动取消注释）、编码器采样心跳、SPI 帧失败计数、CAN 运行统计 |

> 注：`foc.h` 中 `FOC_CLOSEDLOOP_ENABLE = 0`，当前固件处于**硬件验证/开环调试阶段**，闭环代码已就绪但默认未启用。
> 启用闭环前还需先接入输出端编码器：位置环反馈读取的 `Encoder2_Angle_Multiturn` 现在恒为 0（`Encoder2_UpdateAngle()` 无调用点）。

| **GPIO / EXTI** | `ENABLE`(PA11，DRV8353 使能，**高电平使能 / 拉低进睡眠，上电默认低**)、`nFAULT`(PA12，下降沿 EXTI，优先级最高 0)、`LED`(PB9，低点亮)、`PWM_COTR`(PB12，DRV8353 PWM 控制脚，初始化期间保持低)、三个片选（ME_CS/DRV_CS/ME2_CS，推挽，空闲高） |

### 控制与保护要点

- **状态机** `FOC_State_t`（扁平 7 态，**枚举值即对外统一编号**）：
  `0`IDLE `1`OPENLOOP `2`ALIGN `3`TORQUE（闭环力矩）`4`SPEED（闭环速度）`5`POSITION（闭环位置）`6`FAULT。
  闭环三态按**级联深度递增**（`TORQUE=3 < SPEED=4 < POSITION=5`），故直接用 `foc.mode >=` 判深度：
  `TORQUE`=仅电流环 / `SPEED`=+速度环 / `POSITION`=+位置环。
- **模式编号**：串口 / CAN / 上报 / 保护共用同一套，且**直接使用 `(int)foc.mode`**，不再有任何映射函数。
- **保护项**：堵转(三相合成幅值 >36A 且 |转速| <3 rad/s)、编码器样本过期(连续 100 拍未接受有效角度，包括 SPI 失败 / 无效 raw / 野值，≈5ms)、通讯失联(CAN 心跳 20ms 超时)、
  过温(90℃ 关断 / 70℃ 恢复)、母线过压(>32V)、欠压(<16V)、超速(230 rad/s)、单相峰值(40A)、I²t 热积累、
  位置跟随误差、软限位，外加 DRV8353 硬件 nFAULT。
  其中前 3 项（相峰值 / 堵转 / I²t）每拍巡检（20kHz），其余 7 项按 `control_tick % 10` 降至 **2kHz**。
- **故障码** `FAULT_CODE_*`：0 无 / 1 硬件 / 2 堵转 / 3 编码器 / 4 过温 / 5 过压 / 6 欠压 / 7 超速 /
  8 相过流 / 9 I²t / 10 位置误差 / 11 软限位 / 12 通讯超时。
- **故障掩码** `fault_mask`：位 n = `FAULT_CODE_n`（n=1..12，`FAULT_MASK_BIT()`）。`fault_code` 单值会
  被后写覆盖，掩码则累积一次故障事件内**触发过的全部保护**，随 `fault_code` 在上报后一同清零；
  串口打印为 `mask=0xXXX {A|B|C}`。
- **恢复策略**：`FOC_STATE_FAULT` 指数退避（`2^(n-1) × 2s`，封顶 16s），到点后按温度 / 母线 / 转速 / I²t
  四项判据复检（另要求编码器样本重新有效），通过后由中断统一 `FOC_SetMode(FOC_STATE_IDLE)` 回 **IDLE**
  并清空目标速度 / 电压（重新走斜坡缓启动，不会直接跳回开环满输出）；阻塞式 `DRV8353_Recover()` 拆到手握手
  （中断判定 → 主循环执行 → 中断收尾），避免在 20kHz 控制中断里长时间丢拍。

### 通信协议

**CAN（FDCAN2 @1Mbps，标准帧）**

- 命令帧 ID = `0x100 + NODE_ID`（0x101~0x10C），反馈帧 ID = `0x200 + NODE_ID`，开环状态帧 ID = `0x300 + NODE_ID`
  （`0x300` 有两种触发：`0x09` 查询响应；以及**转动到位事件自动上报**，后者 `byte7=1`）。
- 故障详情帧 ID = `0x400 + NODE_ID`（0x401~0x40C）：**仅在 `foc.mode == FAULT` 期间发送** —— `0x10` 查询时紧跟 `0x200` 补发一帧；
  进入故障态时**主动上报一次**（需已联机）。携带故障码 / 掩码 / STATUS1/2，无故障时不发，旧上位机可忽略。
- 命令码（数据区 byte0）：`0x01` 速度、`0x02` 电压、`0x03` 模式、`0x04` 方向、`0x05` 转矩、`0x06` 位置、
  `0x07` 开环转角度并悬停、`0x08` 心跳、`0x09` 查开环状态、`0x10` 请求反馈。
- 完整字节编码、示例帧与上位机（Linux SocketCAN / python-can）示例见下文
  [CAN 上位机控制指令说明](#can-上位机控制指令说明)。

**串口（USART3 @115200）**：`help` `fault` `v=` `s=` `t=` `mode=` `dir=` `status` `can` `log=`
`pid [ring Kp Ki Kd]` `enable` `disable` `ang=`（行尾 `\r`/`\n`）。

- `v=<V>`：设开环电压；**非零值启动 3s 自动归零**（`AUTO_STOP_MS = 3000`，到点打印 `[AUTO STOP]` 并把电压归零），`v=0` 取消计时。
- `s=` / `t=` / `mode=` / `dir=`：与 CAN 的 `0x01` / `0x05` / `0x03` / `0x04` 同语义，直接改同一份 `foc` 状态（串口侧不受开环门控约束）。
- `log=1`：每 **200ms** 自动打印一行状态（`Ia/Ib/Ic`、母线电压、NTC 温度、转速、模式、注入组原始值、`InjMiss`）；发送缓冲余量 <160 字节时跳过本次，避免挤掉命令回显。
- `pid`：打印 `speed` / `id` / `iq` / `pos` 四环；`pid <ring> <Kp> <Ki> <Kd>` 在线改参（`ring` = `speed|id|iq|pos`，只改 RAM，复位后恢复 `foc.c` 初值）。
- `enable`：`DRV8353_Recover()` + 切 **开环** + `Protect_CommDisarm()`（关闭失联保护）；`disable`：只拉低 `ENABLE` 关栅极驱动。
- `ang=<deg>`：阻塞式开环测试命令（转向输出端角度 → 电弹簧保持 **3s** → 自动释放），执行期间主循环被占用。
- `status`：运行快照（转速、角度、三相电流、`Id/Iq`、模式、目标速度、电压、母线、NTC、对齐零点 / 方向、注入组原始值与 `InjMiss`、`TXdrop`）；`can`：FDCAN 实时诊断；`fault`：读 DRV8353 STATUS1/2。

> ⚠️ **CAN 联机后串口被屏蔽**：`Protect_CommIsArmed()`（收到过任一 CAN 帧）为真时，主循环跳过全部串口处理
> （命令解析、`status` / `log=` / 故障自动上报都停），并丢弃期间累积的输入。该标志只有上电初值为 0，
> 因此一旦接入过 CAN，只能**断电重启且不再接收 CAN 帧**后才能继续用串口（`enable` 也必须在 armed = 0 时发）。

## CAN 上位机控制指令说明

> 适用对象：STM32G474 关节电机驱动器（FOC 固件）
> 面向读者：上位机侧（RK3588S / 主控）开发与调试人员
> **本文重点：上位机如何通过 CAN 发送控制指令。**

---

### 1. 概述与当前启用状态

- 下位机通过 **FDCAN2** 与上位机通讯，采用 **经典 CAN（Classic CAN，非 CAN FD）**、**11 位标准帧**。
- 每块驱动板有一个**编译期固定**的节点号 `NODE_ID`（1 ~ 12）。
- 通讯基本是**一问一答式**（例外是两类事件会由下位机**主动上报**：开环到位、进入故障态）：
  - 上位机向 `0x100 + NODE_ID` 发送**命令帧**（下称"指令"）；
  - 下位机向 `0x200 + NODE_ID` 发送**状态反馈帧**（`0x10` 的响应）；
  - 下位机向 `0x300 + NODE_ID` 发送**开环动作状态帧**（`0x09` 的响应 + 到位事件自动上报，独立帧 ID）；
  - 下位机向 `0x400 + NODE_ID` 发送**故障详情帧**（故障态下 `0x10` 查询的附加帧 + 进入故障态时主动上报一次）；
  - ⭐ **到位事件**：`0x07` 转动到位进入悬停保持的瞬间，下位机**主动**发一帧 `0x300 + NODE_ID`（`byte0=2`、`byte7=1`），无需查询；
  - 节点号编码进帧 ID，由硬件过滤器自动区分，同一总线上的多个电机互不干扰。

> ✅ **当前启用状态（已启用）**
> 应用层代码已实现，且 `Core/Src/main.c` 中初始化与主循环调用**均已启用**，**无需再手动取消注释**：
> - `USER CODE BEGIN 2` 中的 `FDCAN_App_Init();`
> - 主循环中的 `FDCAN_App_Process();`
> - 总线错误监测（Error Warning / Error Passive / Bus Off / 协议错误）与**总线关闭（BusOff）自动恢复**同样已启用，见 [2.1](#21-总线错误监测与-busoff-自动恢复)。
>
> 核对方法见 [第 9 章](#9-附录can-的启用与检查)。

### 2. 总线与硬件参数

| 项目 | 值 | 说明 |
|---|---|---|
| 外设 | **FDCAN2** | |
| 引脚 | **PB5 = FDCAN2_RX**，**PB6 = FDCAN2_TX** | AF9 |
| 时钟源 | PCLK1 = **72 MHz** | HSE 8MHz × PLLN18 / PLLR2 |
| 帧格式 | **经典 CAN** | 非 CAN FD，数据段 ≤ 8 字节 |
| 工作模式 | Normal | 正常收发 |
| 波特率 | **1 Mbps** | Prescaler=9，TS1=5，TS2=2（采样点 75%） |

| 协议异常处理 | **关闭**（`ProtocolException=DISABLE`） | 协议异常**不**自动进入总线关闭；固件另开启**诊断用**协议错误中断，仅累计错误次数 |

| 标准过滤器个数 | 1 | 掩码模式精确匹配 `0x100 + NODE_ID`，投递 RX FIFO0 |
| 全局过滤器 | **拒绝不匹配帧** | `NonMatchingStd/Ext = Reject`，远程帧同样拒绝：其他节点的命令帧不会进入本节点 |
| 接收队列 | 16 帧深（软件） | 中断内一次读空 RX FIFO0 入队，主循环按到达顺序全部执行，突发指令不互相覆盖 |
| 中断 | `FDCAN2_IT0` / `FDCAN2_IT1` | 优先级均 3 |

> 波特率换算：`f_bit = 72MHz / (Prescaler × (1 + TS1 + TS2)) = 72e6 / (9 × 8) = 1 Mbps`。
> 上位机侧请将 CAN 控制器配置为 **1 Mbps**、经典帧，否则收发异常。

#### 2.1 总线错误监测与 BusOff 自动恢复

下位机对总线错误做了**监测 + 自愈**，上位机联调时需了解其行为：

- **错误分级监测**（状态变化时进中断，仅记录、不阻塞）：Error Warning（TEC>96 或 REC>96）、Error Passive（TEC>127 或 REC>127）、Bus Off（节点离线）。
- **诊断变量**（固件内部维护）：
  - `fdcan_error_flags`：当前错误标志位，bit0 = 错误警告(EW)、bit1 = 错误被动(EP)、bit2 = 总线关闭(BO)；
  - `fdcan_tec` / `fdcan_rec`：发送/接收错误计数；
  - `fdcan_busoff_count`：累计进入总线关闭次数；
  - `fdcan_proto_err`：协议错误（仲裁段/数据段）累计次数。
  - ⚠️ 以上变量**当前不经 CAN 上报**：`0x200` / `0x300` 反馈帧均无对应字段，只能通过本地调试（串口/调试器）读取，上位机不要按不存在的字段解析。
- **总线关闭自动恢复流程**（在 `FDCAN_App_Process()` 中，主循环执行）：
  1. 检测到 BO 标志 → 先清标志（防死循环）；
  2. `HAL_FDCAN_Stop()` → `HAL_FDCAN_Start()`，由硬件等待总线空闲后自动退出总线关闭；
     - `Stop` 的返回值被**忽略**：`State != BUSY` 时它必然返回失败，但只要成功进入 INIT，随后的 `Start` 即可把外设拉回运行态；
     - `HAL_FDCAN_Start` 本身**没有超时等待**（只清 `CCCR.INIT` 后立即返回），失败只可能是 `State` 异常，**不会是"总线繁忙"**；
  3. 恢复成功则重新激活接收/错误中断通知；
  4. 若 `Start` 失败（`State` 异常，例如 `Stop` 超时被置为 `ERROR`），改用 `HAL_FDCAN_Init()` + `FDCAN_App_Init()` **整外设重新初始化**（过滤器、全局过滤器、中断线一并重配），从根上避免恢复逻辑永久卡死；
  5. 若最终仍未进入 `BUSY` 运行态，重新置回 BO 标志，**下个主循环周期继续重试**。
- **对上位机的影响**：节点处于 BusOff 期间**完全不收发**；恢复瞬间与重试期间发出的帧可能丢失。关键指令（尤其 `0x07` 类动作命令）建议做重发或按反馈帧确认（见 [第 8 章](#8-注意事项与常见坑)）。

### 3. 节点编址

- 节点号：`NODE_ID`，取值 **1 ~ 12**，在 `Core/Inc/fdcan_app.h` 中 `#define NODE_ID 1`。
- 设计上两路 CAN 各挂 6 个关节，节点号全局唯一。

| 帧方向 | 帧 ID 计算 | 取值范围（NODE_ID=1~12） |
|---|---|---|
| 命令帧（上位机 → 电机） | `0x100 + NODE_ID` | `0x101` ~ `0x10C` |
| 状态反馈帧（电机 → 上位机） | `0x200 + NODE_ID` | `0x201` ~ `0x20C` |
| 开环动作状态帧（电机 → 上位机） | `0x300 + NODE_ID` | `0x301` ~ `0x30C` |
| 故障详情帧（电机 → 上位机） | `0x400 + NODE_ID` | `0x401` ~ `0x40C` |

**过滤规则（下位机侧，三重保护）**：

1. **硬件过滤器**：仅接收 `CMD_FRAME_ID = 0x100 + NODE_ID` 的帧（掩码模式，`FilterID2 = 0x7FF` 全位精确匹配），投递到 RX FIFO0；
2. **全局过滤器**：不匹配任何过滤器的帧（含扩展帧、远程帧）一律**拒绝**，不会进入接收队列；
3. **接收中断内复核帧 ID**：只处理 `CMD_FRAME_ID` 的帧。

因此**发错 ID 的帧会被下位机直接丢弃**；同一总线上其他节点的帧既不执行、也不刷新本节点的心跳，**不会互相"串台"**。

**接收队列（突发多帧不再互相覆盖）**：接收中断把每一帧放入 16 帧深的软件队列，主循环按**到达顺序**逐条执行完所有积压帧，详见 [4.1](#41-统一帧格式) 与 [8](#8-注意事项与常见坑) 第 15 条。

### 4. 上位机发送控制指令（重点）

#### 4.1 统一帧格式

所有控制指令使用**同一种帧格式**：

| 项 | 要求 |
|---|---|
| 帧类型 | 数据帧 |
| ID 类型 | **标准帧（11 位 ID）** |
| ID 值 | `0x100 + NODE_ID` |
| 数据长度 | **DLC = 8（必须固定 8 字节）** |
| 字节 0 | **命令码** |
| 字节 1 ~ 7 | 命令参数（**小端，低字节在前**）；未用到的字节填 `0` |

> 📌 **建议固定发满 8 字节（DLC = 8）**，未用到的字节填 `0`。固件侧已对短帧补零（DLC < 8 时未用字节按 `0` 解析，不再是上一帧残留数据），但仍建议统一发满 8 字节；`0x07` 另有 `DLC ≥ 3` 的短帧保护，DLC 过小会被直接忽略。
>
> 📌 **可连发，但仍建议留间隔**：下位机接收侧已改为**队列化**（16 帧深），`0x03` 切模式 + `0x02` 设电压 + `0x07` 转角度这类连发**不会再互相覆盖**，且严格按到达顺序执行。不过仍建议**逐条发送、间隔 ≥2 ms**（或收到反馈后再发下一条）：降低总线瞬时负载，避免 3 级 TX FIFO 溢出导致反馈帧被丢弃。

#### 4.2 命令码总表

| 命令码 | 宏名 | 含义 | 参数编码 | 单位 |
|---|---|---|---|---|
| `0x01` | `CMD_SET_SPEED` | 设置目标速度 | byte1-2 = `int16` | rad/s **×10** |
| `0x02` | `CMD_SET_VOLTAGE` | 设置开环电压 | byte1-2 = `int16` | V **×100** |
| `0x03` | `CMD_SET_MODE` | 切换控制模式 | byte1 = `uint8` | 见下 |
| `0x04` | `CMD_SET_DIRECTION` | 设置方向 | byte1 = `uint8` | 0=正转，1=反转 |
| `0x05` | `CMD_SET_TORQUE` | 设置目标转矩 | byte1-2 = `int16` | Nm **×100** |
| `0x06` | `CMD_SET_POSITION` | 设置目标位置 | byte1-4 = `int32` | rad **×10000** |
| `0x07` | `CMD_SET_OPENLOOP_ANGLE_HOLD` | 开环转到指定输出端角度并悬停保持 | byte1-2 = `int16` | 度 **×10** |
| `0x08` | `CMD_HEARTBEAT` | 心跳（维持联机，不改变运行状态） | 无 | — |
| `0x09` | `CMD_GET_OL_STATUS` | 查询开环动作状态 | 无 | — |
| `0x10` | `CMD_GET_STATUS` | 请求状态反馈 | 无 | — |

> ⭐ `0x07` 转动到位（RUN→HOLD）时，下位机会**主动**发一帧 `0x300 + NODE_ID`（`byte0=2`、`byte7=1`）；`0x09` 查询响应的 `byte7=0`。

> ⚠️ `0x01` / `0x02` / `0x07` 受**开环门控**约束，只在开环模式下生效，详见 [4.5 开环门控规则](#45-开环门控规则重要行为变更)。

**`0x03` 模式编号（byte1）**

| 值 | 模式 | 说明 |
|---|---|---|
| `0` | IDLE | 空闲，无输出 |
| `1` | 开环 | 开环电压/速度驱动 |
| `2` | 对齐 | 转子两步对齐 |
| `3` | 闭环力矩 | 直接给定 Iq |
| `4` | 闭环速度 | 速度环 → 电流环 |
| `5` | 闭环位置 | 位置环 → 速度环 → 电流环 |
| `6` | 故障 | 仅出现在**反馈 byte5**（命令 `0x03` 不接受 `6`） |

> 📌 上表各值**就是 `FOC_State_t` 枚举值本身**，也被 [5.1 状态反馈帧](#51-状态反馈帧0x10-的响应0x200--node_id) 的 **byte5** 直接使用：下位机**直接写入 `(int)foc.mode`**，无需任何转换函数，**与命令 `0x03` byte1 完全一致**，上位机可直接用同一套编号比较/回填。

#### 4.3 逐条命令的字节编码

所有数值均为**有符号**、**小端（低字节在前）**、**二进制补码**。

##### 4.3.1 `0x01` 设置目标速度（int16，rad/s ×10）

```
byte0 = 0x01
byte1 = (int16_val >> 0) & 0xFF
byte2 = (int16_val >> 8) & 0xFF
byte3..byte7 = 0
其中 int16_val = 目标速度(rad/s) × 10
```
- 例：目标 `10.0 rad/s` → `10 × 10 = 100 = 0x0064` → `byte1=0x64, byte2=0x00`

##### 4.3.2 `0x02` 设置开环电压（int16，V ×100）

```
byte0 = 0x02
byte1..2 = int16(电压(V) × 100)，小端
```
- 例：`0.6 V` → `0.6 × 100 = 60 = 0x003C` → `byte1=0x3C, byte2=0x00`
- **受开环门控**：仅在开环模式（`mode = 1`）生效，非开环时静默忽略（见 [4.5](#45-开环门控规则重要行为变更)）。
- **`0` 的语义**：发 `0x02` 且电压为 `0`（`byte1=0x00, byte2=0x00`）会**释放**正在进行的"转角度/悬停保持"动作（见 4.3.7），并把电压、速度归零。

##### 4.3.3 `0x03` 设置控制模式（uint8）

```
byte0 = 0x03
byte1 = 模式编号（0~5，见上表）
```
- 例：切到开环 → `byte1 = 0x01`

##### 4.3.4 `0x04` 设置方向（uint8）

```
byte0 = 0x04
byte1 = 0x00（正转）或 0x01（反转）
```
- 实现：对当前速度给定取符号（正转取 |v|，反转取 -|v|）。一般设置速度时可带符号，此命令用于不改变幅值地翻转方向。

##### 4.3.5 `0x05` 设置目标转矩（int16，Nm ×100）

```
byte0 = 0x05
byte1..2 = int16(转矩(Nm) × 100)，小端
```
- 例：`1.0 Nm` → `100 = 0x0064` → `byte1=0x64, byte2=0x00`

##### 4.3.6 `0x06` 设置目标位置（int32，rad ×10000）

```
byte0 = 0x06
byte1 = (int32_val >> 0)  & 0xFF
byte2 = (int32_val >> 8)  & 0xFF
byte3 = (int32_val >> 16) & 0xFF
byte4 = (int32_val >> 24) & 0xFF
byte5..byte7 = 0
其中 int32_val = 目标位置(rad) × 10000
```
- 例：`1.0 rad` → `10000 = 0x00002710` → `byte1=0x10, byte2=0x27, byte3=0x00, byte4=0x00`

##### 4.3.7 `0x07` 开环转到指定输出端角度并悬停保持（int16，度 ×10）

```
byte0 = 0x07
byte1 = (int16_val >> 0) & 0xFF
byte2 = (int16_val >> 8) & 0xFF
byte3..byte7 = 0
其中 int16_val = 目标输出端角度(度) × 10   （有符号：正=正转，负=反转；0 视为无效被忽略）
```
- 角度是**相对当前输出端位置**的相对量（非绝对零点）。
- **必须先处于开环模式**（`0x03` byte1=1），否则本条指令会被静默忽略（见 [4.5](#45-开环门控规则重要行为变更)）。
- **短帧/零值保护**：`DLC < 3` 时直接忽略；角度值 `0` 视为无效、直接忽略（不驱动、不改状态）。
- 运动速度/励磁电压复用 `0x01`/`0x02` 的当前设定；未设定时用缺省值（`8 rad/s` / `0.6 V`）。
- 命令后：按当前开环方式转动 → 到位后进入"电弹簧"悬停保持。

**动作参数与边界（源码宏见 `Core/Inc/foc.h`）**

| 项 | 值 | 说明 |
|---|---|---|
| 减速比 | `GEAR_RATIO_OUT2MOTOR = 12.5` | 输出端 → 电机轴；指令角度按此折算为电机轴电角度 |
| 缺省运动速度 | `FOC_OL_DEFAULT_SPEED = 8 rad/s` | 未设 `0x01`（或速度 < 0.1 rad/s）时使用（电机轴） |
| 缺省电压 | `FOC_OL_DEFAULT_VOLTAGE = 0.6 V` | 未设 `0x02` 时使用 |
| 悬停/回拉电压上限 | `FOC_OL_HOLD_VOLTAGE_MAX = 0.6 V` | 悬停电压 = min(运动电压, 0.6 V)：运动电压更高时悬停被钳到 0.6 V，保持力矩与发热按此上限 |
| 运动阶段超时 | `FOC_OL_MOVE_TIMEOUT_MS = 5000 ms` | **5 s 内未转够角度则直接断电释放**（不会进入悬停） |
| 保持偏差死区 | `FOC_OL_HOLD_BAND_DEG = ±10°`（电机轴） | 超出即触发编码器回拉，≈ 输出端 ±0.8° |
| 回拉滞环 | `FOC_OL_HOLD_HYST_DEG = ±3°`（电机轴） | 回到该范围内即重新冻结保持，≈ 输出端 ±0.24° |
| 回拉速度 | `FOC_OL_HOLD_PULL_SPEED = 3 rad/s`（电机轴） | 低速回拉，避免越过到位点 |
| 单次回拉超时 | `FOC_OL_HOLD_PULL_TIMEOUT_MS = 1000 ms` | 超时即重新冻结保持 |

- **到位判定方式**：按**指令电角度积分**（`|速度给定| × 极对数 × 控制周期` 递减剩余角度）判到位，**不依赖编码器实测**；因此到位时刻与实际机械位置可能存在负载/间隙误差。
- **运动超时**：5 s 内未转够设定角度（如角度过大、负载过重堵转），会**直接断电释放**，状态帧 `0x300` byte0 回到 `0`，不会停在悬停态。
- **悬停不计时自动释放，会一直保持**；释放条件（满足任一即可）：
  1. 发送 `0x02` 且电压为 `0`（`v=0`）——**显式释放**；
  2. 发送 `0x03` 切换到非开环模式（切 IDLE/闭环/对齐），或触发保护停机——自动中止并释放。
  释放后电压、速度归零，状态帧 byte0 回到 `0`（已释放）。
- ⚠️ 悬停期间 d 轴持续通电保持力矩（悬停电压 ≤ `0.6 V`），会持续发热；不需要保持时请及时发送 `v=0` 释放。
- 状态可通过 `0x09` 轮询（见 [5.2](#52-开环动作状态帧0x09-的响应0x300--node_id)）与 [第 6 章](#6-开环转角度--悬停保持完整控制流程)；到位瞬间也会**主动上报**一帧（`byte7=1`）。
- 例：转到 `+90.0°` → `90 × 10 = 900 = 0x0384` → `byte1=0x84, byte2=0x03`
- 例：转到 `-45.0°` → `-450 = 0xFE3E` → `byte1=0x3E, byte2=0xFE`

##### 4.3.8 `0x08` 心跳（无参数）

```
byte0 = 0x08
byte1..7 = 0
```
- 无参数、无反馈、**不改变任何运行状态**，仅用于维持联机心跳（刷新失联计时，见 [第 7 章](#7-心跳与失联保护)）。
- 上位机在空闲/等待期间可周期性发送本命令，避免静默超时停机。

##### 4.3.9 `0x09` 查询开环动作状态（无参数）

```
byte0 = 0x09
byte1..7 = 0
```
- 下位机收到后**立即**回一帧开环动作状态帧（`0x300 + NODE_ID`），格式见 [5.2](#52-开环动作状态帧0x09-的响应0x300--node_id)。
- **不受开环门控限制**：任意模式、任意时刻均可查询。

##### 4.3.10 `0x10` 请求状态反馈（无参数）

```
byte0 = 0x10
byte1..7 = 0
```
- 下位机收到后**立即**回一帧状态反馈帧（`0x200 + NODE_ID`，格式见 [5.1](#51-状态反馈帧0x10-的响应0x200--node_id)）。
- **若此时处于故障态（`byte0 = 2`），紧跟一帧故障详情帧（`0x400 + NODE_ID`）**，携带故障代码/掩码/STATUS1/2，格式见 [5.3](#53-故障详情帧0x10-的响应补充0x400--node_id)。无故障时只回一帧。

#### 4.4 完整示例帧（以 NODE_ID = 1 为例，ID 均为 `0x101`）

| 操作 | 帧 ID | 数据（8 字节，十六进制） |
|---|---|---|
| 设置目标速度 10.0 rad/s | `0x101` | `01 64 00 00 00 00 00 00` |
| 设置开环电压 0.6 V | `0x101` | `02 3C 00 00 00 00 00 00` |
| 切换到开环模式 | `0x101` | `03 01 00 00 00 00 00 00` |
| 切换到对齐模式 | `0x101` | `03 02 00 00 00 00 00 00` |
| 切换到闭环力矩模式 | `0x101` | `03 03 00 00 00 00 00 00` |
| 切换到闭环速度模式 | `0x101` | `03 04 00 00 00 00 00 00` |
| 切换到闭环位置模式 | `0x101` | `03 05 00 00 00 00 00 00` |
| 反转 | `0x101` | `04 01 00 00 00 00 00 00` |
| 设置目标转矩 1.0 Nm | `0x101` | `05 64 00 00 00 00 00 00` |
| 设置目标位置 1.0 rad | `0x101` | `06 10 27 00 00 00 00 00` |
| 开环转到 +90.0° 并悬停保持 | `0x101` | `07 84 03 00 00 00 00 00` |
| 心跳（维持联机） | `0x101` | `08 00 00 00 00 00 00 00` |
| 查询开环动作状态 | `0x101` | `09 00 00 00 00 00 00 00` |
| 请求状态 | `0x101` | `10 00 00 00 00 00 00 00` |
| 设置目标速度 -5.0 rad/s | `0x101` | `01 CE FF 00 00 00 00 00` |

> 负值示例：`-5.0 rad/s × 10 = -50`，补码 = `0xFFCE` → 小端 `CE FF`。
>
> 反馈帧 ID 不同：`0x10` 的响应是 `0x200 + NODE_ID`，`0x09` 的响应是 `0x300 + NODE_ID`（见 [第 5 章](#5-反馈帧)）。

#### 4.5 开环门控规则（重要行为变更）

> ⚠️ **行为变更**：`0x01`（速度）、`0x02`（电压）、`0x07`（转角度）三条指令**只在开环模式下生效**。
> 若当前模式不是开环（`mode ≠ 1`），这三条指令会被**静默忽略**：不驱动电机、也**不回任何反馈**。
> 因此上位机必须**先发 `0x03` 切到开环模式（byte1 = 1）**，再发速度/电压/角度。

| 命令码 | 是否受开环门控 | 说明 |
|---|---|---|
| `0x01` 速度 | ✅ 受控 | 非开环时忽略 |
| `0x02` 电压 | ✅ 受控 | 非开环时忽略 |
| `0x03` 模式切换 | ❌ 不受控 | 任何模式都可切换 |
| `0x04` 方向 | ❌ 不受控 | 任何模式都生效（改速度给定的符号） |
| `0x05` 转矩 | ❌ 不受控 | 任何模式都可设置 |
| `0x06` 位置 | ❌ 不受控 | 任何模式都可设置 |
| `0x07` 转角度悬停 | ✅ 受控 | 非开环时忽略 |
| `0x08` 心跳 | ❌ 不受控 | 任何时候都可发（仅刷新心跳） |
| `0x09` 查询状态 | ❌ 不受控 | 任何模式都可查询 |
| `0x10` 请求反馈 | ❌ 不受控 | 任何模式都可请求 |

- 当前固件 `FOC_CLOSEDLOOP_ENABLE = 0`（闭环禁用），闭环模式会被自动回落为开环；即便如此，仍建议按"先切开环"的顺序操作，以兼容后续启用闭环。
- 任何**离开开环模式**的动作（发 `0x03` 切 IDLE/闭环/对齐、或触发保护停机）都会**立即中止**正在进行的"转角度/悬停"动作并释放输出。

#### 4.6 发送流程（上位机侧）

1. 计算帧 ID：`id = 0x100 + NODE_ID`。
2. 组装 8 字节数据：`data[0] = 命令码`，参数按小端写入，其余补 `0`。
3. 以 **标准帧 / 经典 CAN / DLC=8 / 1 Mbps** 发送。
4. 若需状态，再发一帧 `0x10` 请求，然后接收 `id = 0x200 + NODE_ID` 的反馈帧；若处于故障态，紧跟还会收到一帧 `0x400 + NODE_ID`（故障详情，见 [5.3](#53-故障详情帧0x10-的响应补充0x400--node_id)）。
5. 联机后需**持续周期性发帧**（推荐 1 kHz、最低 ≥50 Hz，见 [第 7 章](#7-心跳与失联保护)），否则下位机会判定通讯失联停机。

#### 4.7 上位机（Linux SocketCAN）示例

```python
# 依赖：pip install python-can   （RK3588S 上通常已启用 can0/can1 接口）
import can
import struct

NODE_ID = 1
CMD_SET_SPEED    = 0x01
CMD_SET_VOLTAGE  = 0x02
CMD_SET_MODE     = 0x03
CMD_SET_TORQUE   = 0x05
CMD_SET_POSITION = 0x06
CMD_GET_STATUS   = 0x10

bus = can.interface.Bus(channel='can0', bustype='socketcan', bitrate=1_000_000)

def send(cmd, payload=b''):
    """payload 为小端字节串；不足 8 字节自动补 0"""
    data = bytes([cmd]) + payload
    data = data.ljust(8, b'\x00')
    msg = can.Message(arbitration_id=0x100 + NODE_ID,
                      is_extended_id=False,          # 标准帧
                      data=data)
    bus.send(msg)

# 设置目标速度 10.0 rad/s（rad/s ×10）
send(CMD_SET_SPEED, struct.pack('<h', int(10.0 * 10)))

# 设置开环电压 0.6 V（V ×100）
send(CMD_SET_VOLTAGE, struct.pack('<h', int(0.6 * 100)))

# 切换到开环模式
send(CMD_SET_MODE, bytes([1]))

# 请求状态
send(CMD_GET_STATUS)
```

### 5. 反馈帧

下位机有**三种**反馈帧，用**帧 ID 区分**，切勿混淆：

| 帧 | 触发方式 | 帧 ID |
|---|---|---|
| 状态反馈帧 | `0x10 CMD_GET_STATUS` 查询 | `0x200 + NODE_ID` |
| 开环动作状态帧 | `0x09 CMD_GET_OL_STATUS` 查询，或**转动到位事件自动上报** | `0x300 + NODE_ID` |
| 故障详情帧 | **故障态**下的 `0x10` 查询（附加帧），或**进入故障态时自动上报** | `0x400 + NODE_ID` |

#### 5.1 状态反馈帧（`0x10` 的响应，`0x200 + NODE_ID`）

- 帧 ID：`0x200 + NODE_ID`，8 字节。
- **仅在收到 `0x10 CMD_GET_STATUS` 时发送一次**，没有周期自动上报，上位机需主动轮询。

| 字节 | 内容 | 编码 |
|---|---|---|
| byte0 | 系统状态 | `0` 空闲/就绪(IDLE)，`1` 运行(对齐/开环/闭环)，`2` 故障(FAULT) |
| byte1-2 | 转速 | `int16`，rad/s ×10（编码器实测 `foc.speed`） |
| byte3-4 | A 相电流 | `int16`，A ×100 |
| byte5 | 控制模式 | **对外统一编号**（= `FOC_State_t` 枚举值，与命令 `0x03` byte1 一致）：`0`IDLE `1`开环 `2`对齐 `3`闭环力矩 `4`闭环速度 `5`闭环位置 `6`故障 |
| byte6-7 | 母线电压 | `int16`，V ×10 |

- 所有多字节字段均为**小端**。
- 解析示例（Python）：

```python
msg = bus.recv(timeout=1.0)
if msg and msg.arbitration_id == 0x200 + NODE_ID:
    d = msg.data
    status      = d[0]                                   # 0/1/2
    speed       = struct.unpack('<h', d[1:3])[0] / 10.0  # rad/s
    current_a   = struct.unpack('<h', d[3:5])[0] / 100.0 # A
    mode_num    = d[5]                                   # 对外统一编号，与 0x03 命令 byte1 一致
    bus_voltage = struct.unpack('<h', d[6:8])[0] / 10.0  # V
```

#### 5.2 开环动作状态帧（`0x09` 的响应，`0x300 + NODE_ID`）

- 帧 ID：`0x300 + NODE_ID`，8 字节；有两种触发：①收到 `0x09 CMD_GET_OL_STATUS` 立即回一帧（`byte7=0`）；
  ②`0x07` **转动到位进入悬停保持**时主动上报一帧（`byte7=1`）。**没有周期上报**。
- 与 `0x200` 状态反馈帧**完全独立**（ID 不同、用途不同），互不影响。

| 字节 | 内容 | 编码 |
|---|---|---|
| byte0 | 动作状态 | `0` 非活动/已释放(IDLE)，`1` 转动中(RUN)，`2` 已到位悬停保持(HOLD)，`3` 回拉中(PULL) |
| byte1-2 | 输出端相对角 | `int16`，**度 ×10（0.1°）**；相对**本次动作起点**；正=正转；IDLE 时填 `0` |
| byte3-4 | 相对悬停点偏差 | `int16`，**度 ×100（0.01°）**；折算到输出端；仅 HOLD/PULL 有效，其余状态填 `0` |
| byte5-6 | 开环设定电压 | `int16`，**V ×100** |
| byte7 | 触发来源 | `0` = `0x09` 查询响应；`1` = 转动到位事件（自动上报） |

- 所有多字节字段均为**小端**、**有符号（二进制补码）**。
- **字段有效条件**（避免误读）：
  - byte1-2「输出端相对角」：**仅 `byte0 ≠ 0`（非 IDLE）时有效**；`byte0 = 0`（已释放）时固定填 `0`。由电机轴多圈机械角差值 ÷ 减速比（`12.5`）推算得到。
  - byte3-4「相对悬停点偏差」：**仅 HOLD(2) / PULL(3) 时有效**，RUN(1) 与 IDLE(0) 固定填 `0`；已折算到减速器输出端。
  - byte5-6「开环设定电压」：所有状态均有效，返回**当前生效值**（悬停/回拉时已被钳到 ≤ `0.6 V` 上限）。
  - byte7：触发来源，`0` = 查询响应、`1` = 到位事件；旧版本固定为 `0`，可按需忽略（向后兼容）。
- 说明：
  - "输出端相对角"是从**电机轴多圈机械角推算**出的相对量（**输出端编码器未启用**），非绝对零点；负载打滑/间隙会带来偏差。
  - "相对悬停点偏差"已**折算到减速器输出端**。内部死区为**电机轴 ±10°**（≈ 输出端 ±0.8°），回拉滞环 **±3°**（≈ 输出端 ±0.24°）。
  - 所有 16 位字段在发送前做**饱和限幅**（±32767），不会因浮点溢出回绕。
- 解析示例（Python）：

```python
msg = bus.recv(timeout=1.0)
if msg and msg.arbitration_id == 0x300 + NODE_ID:
    d = msg.data
    ol_state = d[0]                                      # 0/1/2/3
    evt      = d[7]                                      # 0=0x09 查询响应, 1=转动到位事件
    rel_deg  = struct.unpack('<h', d[1:3])[0] / 10.0     # 输出端相对角（度）
    dev_deg  = struct.unpack('<h', d[3:5])[0] / 100.0    # 相对悬停点偏差（度，输出端）
    ol_volt  = struct.unpack('<h', d[5:7])[0] / 100.0    # 开环设定电压（V）
    # ol_state 含义：0=已释放 1=转动中 2=悬停保持 3=回拉中
    # evt=1 且 ol_state=2 表示"刚到位并进入悬停保持"（自动上报）
```

#### 5.3 故障详情帧（`0x10` 的响应补充，`0x400 + NODE_ID`）

- 帧 ID：`0x400 + NODE_ID`，8 字节。
- **只在故障态发送**（`0x200` 的 byte0 = `2` / byte5 = `6`）：
  - ① 收到 `0x10` 查询时，**紧跟**状态反馈帧补发一帧（同一故障期间每次查询都会带，便于上位机确认"仍在故障中"）；
  - ② **进入故障态时主动上报一帧**（同一次故障事件仅一帧，且仅在已联机时推送）。
- 故障恢复（指数退避结束后自动切回 IDLE）后不再发送，`0x200` 的 byte0 恢复为 `0`；不认识本帧的旧上位机直接忽略即可，**向后兼容**。

| 字节 | 内容 | 编码 |
|---|---|---|
| byte0 | 故障码 | `1`HARDWARE `2`STALL `3`ENCODER_STALL `4`OVERTEMP `5`OVERVOLT `6`UNDERVOLT `7`OVERSPEED `8`PHASE_OC `9`I2T `10`POS_ERROR `11`SOFT_LIMIT `12`COMM_TIMEOUT |
| byte1 | 状态位 | bit0 = 当前仍在故障退避中（`1`）；bit1 = STATUS1/2 有效（`1`）；bit2~7 保留 `0` |
| byte2-3 | 故障掩码 | `uint16`，bit n = `FAULT_CODE_n`；同一故障事件内触发过的**所有**保护位（累计，互不覆盖） |
| byte4-5 | DRV8353 STATUS1 | `uint16`，**仅 byte0=1（硬件故障）且 byte1.bit1=1 时有效** |
| byte6-7 | DRV8353 STATUS2 | `uint16`，同上 |

- 所有多字节字段均为**小端**。
- 说明：
  - 故障码/掩码在**故障持续期间保持有效**，故障恢复（离开 FAULT 态）时统一清零，因此本帧只反映"当前这次故障"，不会带出历史故障。
  - `byte1.bit0` 实际恒为 `1`（本帧只在故障态发送）；保留该位是为了让上位机解析逻辑统一、便于后续扩展。
  - 若上位机漏收了主动上报的那一帧，在故障窗口内（退避 ≥ 2 s）继续轮询 `0x10` 即可重新拿到。
  - 掩码 `byte2-3` 的 bit1~bit12 依次对应上表故障码 `1`~`12`（bit n ↔ 故障码 n），例如 `0x0014`（bit2 + bit4）表示本次事件内 **STALL** 与 **OVERTEMP** 同时触发过。

**STATUS1 位定义（byte4-5，`uint16` 小端；有效位 bit10~bit0，bit15~bit11 恒为 0）**

| bit | 掩码 | 名称 | 含义 |
|---|---|---|---|
| 10 | `0x0400` | **FAULT** | 故障状态位（nFAULT 逻辑或）：任一硬件故障锁存即置 1，作总开关用，**不要当独立故障原因** |
| 9 | `0x0200` | **VDS_OCP** | VDS 监视器过流（相电流超过 VDS_LVL 设定，多为堵转/短路） |
| 8 | `0x0100` | **GDF** | 栅极驱动故障（驱动级综合异常） |
| 7 | `0x0080` | **UVLO** | 欠压锁定（VM 供电过低，查母线/供电瞬跌） |
| 6 | `0x0040` | **OTSD** | 过温关断（芯片结温超限，查散热/持续大电流） |
| 5 | `0x0020` | **VDS_HA** | A 相高侧 VDS 过流 |
| 4 | `0x0010` | **VDS_LA** | A 相低侧 VDS 过流 |
| 3 | `0x0008` | **VDS_HB** | B 相高侧 VDS 过流 |
| 2 | `0x0004` | **VDS_LB** | B 相低侧 VDS 过流 |
| 1 | `0x0002` | **VDS_HC** | C 相高侧 VDS 过流 |
| 0 | `0x0001` | **VDS_LC** | C 相低侧 VDS 过流 |

**STATUS2 位定义（byte6-7，`uint16` 小端；有效位 bit10~bit0，bit15~bit11 恒为 0）**

| bit | 掩码 | 名称 | 含义 |
|---|---|---|---|
| 10 | `0x0400` | **SA_OC** | A 相电流采样放大器（CSA）过流 |
| 9 | `0x0200` | **SB_OC** | B 相 CSA 过流 |
| 8 | `0x0100` | **SC_OC** | C 相 CSA 过流 |
| 7 | `0x0080` | **OTW** | 过温**警告**（未关断，先于 OTSD，可做预警） |
| 6 | `0x0040` | **GDUV** | 栅极驱动欠压（VCP / VGLS，电荷泵异常） |
| 5 | `0x0020` | **VGS_HA** | A 相高侧 MOSFET 栅源驱动故障 |
| 4 | `0x0010` | **VGS_LA** | A 相低侧 VGS 驱动故障 |
| 3 | `0x0008` | **VGS_HB** | B 相高侧 VGS 驱动故障 |
| 2 | `0x0004` | **VGS_LB** | B 相低侧 VGS 驱动故障 |
| 1 | `0x0002` | **VGS_HC** | C 相高侧 VGS 驱动故障 |
| 0 | `0x0001` | **VGS_LC** | C 相低侧 VGS 驱动故障 |

- ⚠️ **字段有效条件**：STATUS1/2 是 DRV8353 寄存器的快照，**仅当 `byte0 = 1`（硬件故障）且 `byte1.bit1 = 1`（STATUS 已读到）时有效**。
  其余情况（软件保护：堵转/编码器/过温/母线/超速/过流/I²t/位置/软限位/失联）STATUS1/2 无意义，上位机应只解析 `byte0`（故障码）与 `byte2-3`（掩码）。
- 位与 `0x07FF` 相与即可取有效位；`uint16` 字段为**无符号**（非补码），直接按位判断，不要做符号扩展。

### 6. 开环"转角度 + 悬停保持"完整控制流程

> 前置：`mode` 必须是**开环**（`0x03` byte1=1），否则 `0x01`/`0x02`/`0x07` 会被静默忽略（见 [4.5](#45-开环门控规则重要行为变更)）。

**控制时序**

1. **切开环**：`0x03`，byte1 = `1`。
2. **设电压/速度**（可选，不设则用缺省 `0.6 V` / `8 rad/s`）：`0x02`（V×100）、`0x01`（rad/s×10）。
3. **发角度**：`0x07`，byte1-2 = 输出端角度（度×10，有符号）。下位机开始按当前开环方式转动。
4. **等到位反馈**：
   - **被动方式（推荐）**：不发查询，`0x07` 到位后下位机主动发一帧 `0x300 + NODE_ID`（`byte0=2`、`byte7=1`）；
   - **主动轮询**：周期性发 `0x09`，解析 `byte0`：`1`=转动中 → `2`=到位悬停保持（偏离过大时会短暂出现 `3`=回拉中，随后自动回到 `2`）；
   - 发下一条动作指令前，建议先发 `0x09` 确认当前 `byte0`（`3` = 正在回拉，`1` = 仍在转动）。
   - ⚠️ **运动超时**：`0x07` 发出后 **5 s**（`FOC_OL_MOVE_TIMEOUT_MS`）仍未转够角度，会**直接断电释放**（byte0 回到 `0`，不会停在悬停态）；角度过大 / 负载过重时请调小角度或提高速度、电压。
   - **回拉参数**：偏差超出**电机轴 ±10°** 触发回拉，回拉速度 **3 rad/s**（电机轴），单次回拉最长 **1 s**，回到 **±3°** 滞环内重新冻结保持。
5. **悬停保持（不计时）**：到位后**一直保持、不会自动释放**；期间必须持续发帧维持心跳（`0x08` 心跳或 `0x09` 轮询，推荐 1 kHz、最低 ≥50 Hz，见 [第 7 章](#7-心跳与失联保护)）。
6. **释放**（二选一）：
   - **显式释放**：发 `0x02` 且电压为 `0`（`v=0`）；
   - **切模式中止**：发 `0x03` 切到非开环模式（如 byte1 = `0` 切 IDLE）。
   释放后状态帧 byte0 回到 `0`（已释放），电压、速度归零。

**分步示例（Python）**

```python
import time

def ol_move_and_hold(angle_deg, speed_rad_s=None, voltage_v=None,
                     hold_seconds=2.0, poll_hz=50):
    # 1) 切开环
    send(CMD_SET_MODE, bytes([1]))
    # 2) 设电压/速度（可选）
    if voltage_v is not None:
        send(CMD_SET_VOLTAGE, struct.pack('<h', int(voltage_v * 100)))
    if speed_rad_s is not None:
        send(CMD_SET_SPEED, struct.pack('<h', int(speed_rad_s * 10)))
    # 3) 发角度（度 ×10）
    send(CMD_SET_OPENLOOP_ANGLE_HOLD, struct.pack('<h', int(angle_deg * 10)))

    # 4) 轮询直到进入"悬停保持"（期间持续发帧维持心跳）
    t0 = time.time()
    arrived = False
    while time.time() - t0 < 5.0:               # 固件运动阶段最长 5s，超时会自行断电释放（byte0 回 0）
        send(CMD_GET_OL_STATUS)                 # 每次查询即刷新一帧心跳
        msg = bus.recv(timeout=0.05)
        if msg and msg.arbitration_id == 0x300 + NODE_ID and msg.data[0] == 2:
            print("已到位，开始悬停保持")
            arrived = True
            break
        time.sleep(1.0 / poll_hz)               # 保持 ≥50 Hz（推荐 1 kHz）发帧，避免失联保护停机

    # 5) 悬停不会自动释放：按需保持一段时间（期间仍须发帧维持心跳）
    t_hold = time.time()
    while arrived and time.time() - t_hold < hold_seconds:
        send(CMD_HEARTBEAT)                     # 用空心跳维持联机
        time.sleep(1.0 / poll_hz)

    # 6) 显式释放：发送 v=0
    send(CMD_SET_VOLTAGE, struct.pack('<h', 0))
    print("已释放")

# 转到 +90°，速度 5 rad/s、电压 0.6 V；到位后保持 2 秒再释放
ol_move_and_hold(90.0, 5.0, 0.6, hold_seconds=2.0)
```

> 若只想"发一次再看结果"，也要注意：**任何一次静默超过约 20 ms 都可能触发失联保护**（见 [第 7 章](#7-心跳与失联保护)），请保持周期性发帧（推荐 1 kHz，最低 ≥50 Hz；可用 `0x08` 心跳填充）。

### 7. 心跳与失联保护

下位机带**通讯失联保护**，上位机必须了解并满足：

- 下位机在**每收到一帧**时刷新"通讯心跳"（接收中断内 `Protect_CommFeed()`）。
- **收到首帧之后**失联保护才开始生效（未联机时不误触发）。
- 一旦生效，若连续 **20 ms**（`COMM_TIMEOUT_TICKS = 40`；慢保护每 10 拍巡检一次即 2kHz，40 × 0.5ms = 20ms）
  没有收到任何新帧，则判定通讯失联：
  - 报故障 `FAULT: COMM_TIMEOUT`，
  - **停驱动并进入故障退避**。

**因此**：启用 CAN 并进入联机运行后，上位机应**周期性发帧**（可发任意有效命令帧，如 `0x08` 心跳、`0x09`/`0x10` 查询）：

| 发帧率 | 判定 |
|---|---|
| **1 kHz（每 1 ms 一帧）** | **推荐值**（固件注释的建议节奏，等价于 20 倍于阈值裕量） |
| ≥ 50 Hz（每 ≤ 20 ms 一帧） | 最低下限，仅刚够不触发 20 ms 超时 |
| < 50 Hz（间隔 > 20 ms） | 判定失联，电机保护停机 |

> 阈值 20 ms ≈ 丢失 20 帧，取 20 倍于正常帧间隔，既灵敏又能抗偶发丢帧/中断抖动。

> 本地串口调试时，串口 `enable` 命令会关闭该失联保护；之后 CAN 若再次发帧，保护会自动重新启用。
> 注意 `enable` 只能在**尚未收到过任何 CAN 帧**时发送 —— 一旦 armed，主循环会屏蔽串口输入（见 [通信协议](#通信协议)）。

### 8. 注意事项与常见坑

1. **建议发满 8 字节**：DLC < 8 时未用字节按 `0` 解析（固件已对短帧补零，不再是上一帧残留数据）；`0x07` 额外做了 `DLC ≥ 3` 保护。
2. **反馈 byte5 的模式编号与命令 `0x03` 一致**：均采用对外统一编号（`0`IDLE `1`开环 `2`对齐 `3`闭环力矩 `4`闭环速度 `5`闭环位置 `6`故障），上位机可直接用同一套编号比较/回填。（历史版本曾两套编码并存、需 `FOC_GetModeNumber()` 转换；现已把对外编号直接定为 `FOC_State_t` 枚举值，转换函数已删除。）
3. **三种反馈帧 ID 勿混用**：`0x10` 的响应用 `0x200 + NODE_ID`（故障态下紧跟一帧 `0x400 + NODE_ID`），`0x09` 的响应用 `0x300 + NODE_ID`；只按 `0x200` 收帧会看不到开环动作状态和故障详情。
4. **开环门控**：`0x01`/`0x02`/`0x07` 只在开环模式（`mode=1`）生效，非开环时**静默忽略、不回反馈**；必须先切模式再发参数（见 [4.5](#45-开环门控规则重要行为变更)）。
5. **失联保护阈值约 20 ms**：联机后必须持续发帧（推荐 1 kHz，最低 ≥50 Hz），否则停机；空闲/等待期间可周期发 `0x08` 心跳或 `0x09`/`0x10` 查询来维持心跳。
6. **反馈以轮询为主，两类事件自动上报**：`0x200` 必须发 `0x10` 才回（**故障态下会再附一帧 `0x400`**）；`0x300` 除 `0x09` 查询外，
   `0x07` 转动到位会**主动上报一次**（`byte7=1`）；`0x400` 在**进入故障态时主动上报一次**。回拉(PULL)、释放(IDLE) 等其它状态变化**不会**主动上报，仍需 `0x09` 轮询；
   且主动上报**不喂通讯看门狗**，悬停期间仍须 ≥50 Hz 发帧维持联机。
7. **开环输出端角度是相对量**：`0x07`/`0x09` 中的输出端角度由**电机轴多圈机械角推算**（**输出端编码器未启用**），是**相对本次动作起点**的相对量、非绝对零点；负载打滑/间隙会带来偏差，不要求高精度。
   - 另注意：`0x07` 的**到位判定**按指令电角度积分（不读编码器），因此"已到位"是**给定角度走完**，与实际机械位置可能存在负载/间隙误差。
8. **悬停保持会持续通电发热，且不会自动释放**：电弹簧悬停用 d 轴恒压励磁，悬停电压被钳到 **≤ `0.6 V`**（`FOC_OL_HOLD_VOLTAGE_MAX`，即运动电压高于 0.6 V 时悬停仍只用 0.6 V）；缺省 `0.6 V` 时三相总铜耗约 **3.7 W**（等效相电流约 2.9 A rms，远低于 14 A 额定，不触发 I²t/堵转保护）。悬停**不计时释放**，会一直保持到发 `v=0`（`0x02` 电压 0）或切出开环模式；不需要保持时请及时释放。
   - **运动阶段例外**：`0x07` 发出后 **5 s 内未到位会直接断电释放**（`FOC_OL_MOVE_TIMEOUT_MS`），不会悬停，也不会长时间堵转发热。
9. **NODE_ID 编译期固定**：每块板按关节号分别编译烧录（1~12），上位机需按节点号计算帧 ID。
10. **自动重传关闭**：发送失败不会自动重发，关键指令建议上位机做重发/确认。
11. **波特率必须 1 Mbps**、标准帧、经典 CAN；发扩展帧或 CAN FD 均不被接收。
12. **总线关闭（BusOff）会自愈，但期间会丢帧**：节点进入 BusOff 后**完全不收发**；下位机在主循环里自动 `Stop → Start` 恢复（成功即重新激活中断；若 `State` 异常则 `HAL_FDCAN_Init()` + `FDCAN_App_Init()` 整外设重配；仍失败下周期重试）。恢复瞬间与重试期间发出的帧可能丢失，关键指令（尤其 `0x07` 类动作命令）需重发或按反馈确认（见 [2.1](#21-总线错误监测与-busoff-自动恢复)）。
13. **总线错误诊断信息当前不经 CAN 上报**：错误标志、TEC/REC、BusOff 次数、协议错误计数只在固件内部维护，`0x200`/`0x300`/`0x400` 反馈帧**没有这些字段**；排查总线问题时不要按不存在的字段解析（需本地串口/调试器读取）。**故障码/故障掩码/STATUS1/2 已由 `0x400` 上报**，不属于此处所说的总线错误诊断。
14. **协议异常自动处理已关闭**：`ProtocolException = DISABLE`，协议异常不会自动把节点打到 BusOff；固件仍开启**诊断用**协议错误中断，仅累计计数。
15. **接收已队列化，突发指令不会互相覆盖**：接收中断把每一帧放入 16 帧深的软件队列（中断内一次读空 RX FIFO0），主循环 `FDCAN_App_Process()` 一次按**到达顺序**处理完所有积压帧。因此 `0x03` + `0x02` + `0x07` 连发不会丢帧、也不会错序（不会出现"`0x03` 被覆盖丢失、只剩 `0x07` 因非开环被静默忽略"）。
    - 队列满时**丢弃最新帧**（保持先到先执行的时序），并累加 `fdcan_rx_drop_count`（固件内部变量，不经 CAN 上报）。
    - 正常节奏（≤1 kHz）下该计数应恒为 0；若持续增长，说明发帧速率超过主循环处理能力，请加大发送间隔。
    - 仅 `CMD_FRAME_ID`（发给本节点）的帧才入队、才刷新通讯心跳；其他节点的帧被直接丢弃。

### 2026-10-22 — CAN 故障上报：新增 `0x400` 故障详情帧（`0x10` 查询附带）+ 故障码清零点统一

**背景**：CAN 模式下串口上报整段被屏蔽（`main.c` 的 `if (!Protect_CommIsArmed())`），而 `fault_code`/`fault_mask` 的清零原本写在串口 `UART_FaultReport()` 里，导致 CAN 模式下故障码**永远清不掉**，且上位机查询 `0x10` 时**拿不到故障代码**。

**改动**

1. `Core/Src/uart_cmd.c`：`UART_FaultReport()` 不再清零 `fault_code`/`fault_mask`，改为按故障码去重（`uart_fault_reported_code`），同一故障事件的同一故障码只打印一次，故障恢复后自动复位去重标志（同时消除了持续故障时每 1ms 重复打印的刷屏问题）。
2. `Core/Src/foc.c`：`FOC_SetMode()` 在**离开 FAULT 态**时统一清除 `fault_code`/`fault_mask`/`fault_status_valid`（唯一清零点：自动恢复切 IDLE 与串口 `mode=`、CAN `0x03` 强制切换都走这里），并以 `!fault_triggered` 防止误清同一拍新到的故障。
3. `Core/Src/fdcan_app.c` / `Core/Inc/fdcan_app.h`：新增 `FBK_FAULT_FRAME_ID = 0x400 + NODE_ID` 与 `FDCAN_SendFault()`：
   - `0x10` 查询时若 `foc.mode == FOC_STATE_FAULT`，在 `0x200` 状态帧后**紧跟一帧 `0x400`**（故障码 / 状态位 / 故障掩码 / STATUS1 / STATUS2）；
   - 进入故障态时**主动上报一帧**（每个故障事件一次，TX 失败会在下个主循环重试；仅在已联机时推送）。

**兼容性**：`0x200`/`0x300` 帧格式完全未变；不识别 `0x400` 的旧上位机直接忽略即可。

### 2026-10-22 — 编码器刷新移入 TIM1 20kHz 中断：快/慢双路径 + 一拍延迟补偿、ISR 打点清理

**背景**：闭环前置遗留项「换相角度源仍由主循环 1kHz 刷新，额定转速下电角频率 ≈639Hz 存在混叠」。
编码器已改为单帧流水线（1 帧 ≈1.78µs @9MHz），SPI1 有余量承担 20kHz 采样；
同时 `[TEMP]` 的 ISR 耗时打点（`t_body/t_sense/t_foc/t_led_max`、`isr_cyc_*`、串口 `isr` 命令）已完成使命，一并移除。

**改动**

1. `Core/Src/kth7823.c` / `Core/Inc/kth7823.h`：新增 `KTH7823_Tick(uint32_t tick)`，**仅由 TIM1 20kHz 中断调用**（SPI1 单一所有者）：
   - **每拍**：`spi_exchange_frame(0x0000)` 读 1 帧 → 0x0000/0xFFFF 计为无效读数（正常清零）→ 16 位带符号差值做多圈解包裹（跳变超 `KTH7823_UNWRAP_MAX_DELTA=1024` 判野值丢弃）→ 更新 `KTH7823_Angle_Multiturn`；
   - **每拍**：用相邻两个有效帧的 DWT 间隔算角速度 ω，外推
     `KTH7823_Angle_Multiturn_Comp = angle_unwrapped + ω × (KTH7823_ANGLE_DELAY_PERIODS × control_dt)`
     （单帧流水线固有滞后 1 拍 = 50µs；ω 限幅 ±400 rad/s 防坏帧飞出）；
   - **每 20 拍（≈1kHz）**：DWT 差分测速（窗口 ≈1ms，避免逐拍量化噪声）+ `encoder_update_count++`。
2. SPI 收发改为**寄存器级 + DWT 限时**（`KTH7823_SPI_TIMEOUT_US = 10`）：HAL 的毫秒超时依赖 SysTick（优先级 15），在 TIM1 中断里无法推进，一旦卡住会永不返回、把 PWM 冻结在最后占空比。失败路径读 `DR`/`SR` 清 `OVR`、关开 `SPE` 复位 FIFO，并累加 `kth7823_spi_err_cnt`（现场快照 `kth7823_diag_cr1/sr`）；`spi_in_frame` 拒绝重入，绝不并发拉 CS。
3. 慢路径 `KTH7823_SlowUpdate()` 留在主循环（≈1kHz）：只读中断缓存的 raw 做 sin/cos 一阶低通 + atan2 → `KTH7823_Angle_Rad/_Deg`（开环起始角、对齐平均、上报）。实测该段 ≈7µs，放进 20kHz 会顶穿 50µs 预算；α 语义不变。
4. `KTH7823_RAW_FAULT_LIMIT` 8 → **100 拍**（20kHz 下 ≈5ms，与原「1kHz × 8 次 ≈8ms」同量级，避免提高刷新率后抗扰能力下降 10 倍）。
5. `Core/Src/motor_control.c`：`FOC_TIM1_UpdateIRQHandler()` 顺序改为
   `s_tick` → `KTH7823_Tick(control_tick)` → `CurrentSense_Update()` → `FOC_Update()` → `LED_Update()`（**每 20 拍调用一次**，≈1kHz；LED 按 ms 计时，观感不变，省约 1.2µs/拍）。
6. `Core/Src/foc.c`：闭环（TORQUE/SPEED/POSITION）机械角源改为 `KTH7823_Angle_Multiturn_Comp`；开环悬停/回拉、对齐、上报仍用未补偿的 `KTH7823_Angle_Multiturn`（行为不变）。
7. `Core/Src/main.c`：主循环不再调 `KTH7823_UpdateAngle/UpdateSpeed`，改为 `KTH7823_SlowUpdate()`；`DBG_Monitor_Update()` 当时恢复为每轮调用，但**当前（`main.c:170`）该调用已被注释**，`dbg` 快照不刷新，需要观察时再手动取消注释。
8. `Core/Src/uart_cmd.c`：阻塞式 `ang=` 测试的三个循环不再自己发起 SPI 帧（中断已持续刷新角度），只保留喂狗 + 串口泵；删除 `isr` 命令与 `status` 末尾的 ISR 耗时附行。
9. `Core/Src/stm32g4xx_it.c`：删除 `isr_cyc_max/min/cnt/over_cnt/sum` 打点变量。

**影响**

- 20kHz 中断新增约 3~4µs（1.78µs 编码器帧 + 解包裹/外推），相对 50µs 预算仍有余量；SPI1 占用率约 3.6%。
- 角度与电流环**同拍更新**，闭环角度源的混叠问题消除；读数固有滞后 1 拍由 `_Comp` 外推补偿，`KTH7823_ANGLE_DELAY_PERIODS` 可台架微调（0.5~1.5）。
- 编码器保护使用 `kth7823_stale_ticks` 跟踪有效样本年龄；SPI 失败、无效 raw 和解包裹野值都不会清零。连续 100 拍未更新即停机，恢复前必须重新收到有效样本。
- `FOC_CLOSEDLOOP_ENABLE` 仍为 **0**，闭环功能本身未启用。

**验证（台架待做）**

- Keil 编译 0 Error；`dbg.control_tick` 稳定增长、`dbg.tick` 与 1ms 节拍同步（**需先取消 `main.c` 中 `DBG_Monitor_Update()` 的注释**）。
- `status` 的 `InjMiss` 长期 0、静止时 `Speed≈0`、`dbg.kth_raw_fault_cnt` 长期 0、`kth7823_spi_err_cnt` 长期 0。
- 手转电机轴：`kth7823_unwrap_glitch_cnt` 不应持续增长；`kth7823_diag_cr1/sr` 应为 0（无失败帧）。
- 开环 `v=`/`ang=` 行为与改动前一致；串口 `ang=` 阻塞期间 LED 仍按状态机刷新。

**关联文件**：`Core/Inc/kth7823.h`、`Core/Src/kth7823.c`、`Core/Src/motor_control.c`、`Core/Src/foc.c`、
`Core/Src/main.c`、`Core/Src/uart_cmd.c`、`Core/Src/protect.c`（注释）、`Core/Src/stm32g4xx_it.c`。

### 2026-10-22 — 采样链复查收尾：JEOS 写清、母线采样时间、ADC2 中断开销、零偏校验

**背景**：复查 10-21 的采样链重构，发现 4 个问题：

1. **`JEOS` 从来不会被清除**。`CurrentSense_Update()` 判 `JEOS` 后只读 JDR，没有任何清零动作。
   STM32G4 的 `ADC_ISR` 是 **w1c** 架构（`stm32g4xx_hal_adc.h`：“bit cleared by writing 1 (writing 0 has no
   effect on any bit of register ISR)”），且读 `JDRx` **只清 `JEOC`**、不清 `JEOS`
   （RM0440 `ADC_ISR` bit5 JEOC：“cleared by software writing 1 to it **or by reading the corresponding
   ADC_JDRy register**”；bit6 JEOS 只有“cleared by software”；HAL 的
   `HAL_ADCEx_InjectedGetValue()` 文档亦明确“does not clear ADC flag JEOS”）。
   后果：`JEOS` 从第一次注入序列完成起永久为 1，`adc_inj_miss_cnt`（串口 `InjMiss`）**恒为 0** ——
   而它正是判断“提前量 `CCR4` 是否足够 / TIM1_CH4 触发链是否接通”的唯一量化指标，
   即上一次重构的核心验收项实际是失效的。
2. **母线 CH8 采样时间偏短**：CH8 经 100kΩ 串阻进 ADC，源阻抗 ≈100k，
   24.5cyc（0.68µs）≈1.36τ（τ=100k×5pF=500ns），而 12 位需要 ≈8.3τ。
3. **ADC2 链路中断开销**：`HAL_ADC_Start_DMA()` 会同时打开 TC/HT，一条 1ms 才用一次的温度通道
   却按 20kHz 产生 40k 次/秒中断。
4. **零偏标定无合理性判断**：64 次平均结果被无条件信任，标定时电机若被外力带动会静默标错。

**改动**

1. `Core/Src/sense.c` `CurrentSense_Update()`：判标志 → 读 `JDR1/JDR2` → **`ADC1->ISR = ADC_ISR_JEOS;`**
   - w1c 写 1 清，编译为单条 STR，只清 bit6；
   - **禁止写成 `ADC1->ISR |= ADC_ISR_JEOS;`**：读-改-写会把当前所有置位标志（`OVR`/`JEOC`/`AWDx`）一起清掉；
   - 每拍清一次后，`InjMiss` 才真正具备诊断能力（正常长期 0；提前量不足或触发链断则 20kHz 增长）。
2. `Core/Src/adc.c` + `Drive.ioc`：CH8 采样时间 24.5cyc → **`ADC_SAMPLETIME_247CYCLES_5`**（6.9µs ≈13.8τ）；
   CH4（MOS NTC）保持 24.5cyc（源阻抗 10k‖10k=5k，0.68µs 已是 27τ，足够）。
   规则组总耗时变为 (24.5+12.5 + 247.5+12.5)/36MHz = **8.25µs**，仍远小于到下一次 CC4 触发的 46µs。
3. `Core/Src/sense.c` `CurrentSense_Init()`：ADC2 启动后
   `__HAL_DMA_DISABLE_IT(hadc2.DMA_Handle, DMA_IT_TC | DMA_IT_HT | DMA_IT_TE)` ——
   循环搬运保留（`adc2_values_ntc[0]` 仍每 50µs 刷新），只关中断，省 40k 次/秒。
4. `Core/Inc/sense.h` + `Core/Src/sense.c`：新增零偏合理性校验（**不阻塞**，只置标志）。
   阈值 **`I_OFFSET_MAX_A = 2.5 A`**（1 LSB = 40.3 mA，2.5 A ≈ 62 counts ≈ 50 mV）
   + **`I_OFFSET_DIFF_MAX_A = 1.0 A`**（两相零偏差值，专抓单通道故障：某相 shunt / 走线 / INA240）。
   误差预算（0 A 时）：INA240A1 Vos ±25µV ≈ **0.001 A**；VREF 1% 分压误差 ≈ **0.83 A**；
   ADC 失调 ≈ **0.1 A**；故障量级为 **±82.5 A**（注入组未启动 / INA240 输出开路或饱和）。
   - 超限只置 `sense_hw_error`，**不再 `Error_Handler()`**：IWDG（≈1s）复位会造成上电复位循环，
     台架表现为“不亮灯 / 无串口”，反而更难排查；
   - `sense_hw_error` 由 `MotorControl_CommandGate()`（拒绝控制命令，UART/CAN 同一入口）与
     `MotorControl_BootIsHwError()`（LED 慢闪）消费，与 `boot_hw_error` 同一通路；
     `MotorControl_BootSequence()` 额外打印实测零偏值与排查提示，并 `DRV8353_Disable()` +
     `Protect_StopPWM()`（标定不可信时不让功率级带电待命：三相下桥全通且电流读数本身带偏置）；
   - 新增观测量 `cal_offset_A/B`（单位 A，标定结果快照）；20kHz 热路径仍用 `static` 变量，
     避免中断里因 `volatile` 反复重载。
5. `Core/Inc/sense.h`：统一导出 `sense_hw_error` / `cal_offset_A` / `cal_offset_B`
   （原由 `motor_control.c` 手写 `extern`，易漏 `volatile`）；删除未使用的 `ADC_TRIG_LEAD_US`；
   时序注释由“推演”改为**实测结论**。

**已验证（结论）**

- 中心对齐 + RCR=1，CNT 上电自 0 起计：**UEV 落在下溢（谷点 CNT=0）**，与设计假设一致；
  故 `CCR4=288`（4µs@72MHz）确实是“UEV 前 4µs”，注入组 2 通道 2.06µs 转换在 UEV 前约 1.94µs 完成，
  FOC 更新中断读到的就是当拍新样本。（若日后改 PWM 模式，需改 PWM2 + `CCR4=ARR-288`。）
- 母线/温度链 CPU 开销归零：ADC2 侧 TC/HT/TE 中断已关；ADC1 侧仍保留（见待办）。

**待办（未做，如实记录）**

- `CurrentSense_Init()` 用 `HAL_TIM_PWM_Start(&htim1, TIM_CHANNEL_4)` 置 CC4E，对 TIM1 **会顺带置 MOE**
  （`stm32g4xx_hal_tim.c:1494-1498`）并重复置 CEN（`1500-1512`）。**已核对：本次不改代码**，
  理由与前置条件见下节“执行流程核对”——换个写法功能等价，收益止于语义，代价是把
  “`Base_Start_IT` 必须先于 `CurrentSense_Init`”从 HAL 自管理降级成隐式契约。
- ADC1 规则组 DMA 的 TC/HT 中断仍在（40k 次/秒，唯一用途是置一次 `adc_dma_ready`），
  探测完成后可同样 `__HAL_DMA_DISABLE_IT(hadc1.DMA_Handle, ...)`。
- 零偏失败时已 `DRV8353_Disable()`，但若 DRV8353 在 sleep 下会拉低 nFAULT，则 nFAULT EXTI 会置
  `fault_triggered` → FOC 进 FAULT → `FOC_FaultRecoverProcess()` 复原并重新使能 EN（等于撤销上面的关断）。
  台架若观察到该现象，需在恢复路径加 `MotorControl_BootIsHwError()` 守卫；本次未改 FOC 状态机，避免扩大改动面。

**已就地修正的注释（原与实况不符）**：`Core/Src/sense.c` 与 `motor_control.c` 中“此时 DRV8353 未使能”
的说法有误 —— `DRV8353_Init()` 早已拉高 `ENABLE`；零偏成立的真实原因是 **TIM1 三路 PWM 未启动（INH 全低）
→ 三相下桥全通 + 转子静止 → 相电流为 0**。这条更正同时说明了“上电瞬间转子被带动会标错零偏”的成因。

**已恢复的注释**：`Core/Src/tim.c` 中 TIM1 的时序约定注释块（`USER CODE BEGIN TIM1_Init 1`，含

CH8 247.5cyc、`CCR4=288` 提前量、CH4 不占引脚、JEOS w1c、`HAL_TIM_PWM_Start` 顺带置 MOE
及其替代写法）此前在整理中被删除，现已恢复并与实测结论一致；`sense.h` 只覆盖“CCR4=提前量”那一半约定。
（注：该注释块中“DRV8353 ENABLE 未拉高”一句与实况不符 —— `DRV8353_Init()` 已在 `MotorControl_Init()`
第 44 行拉高 PA11。按“只改文档、不动代码”的约定暂未回写 `tim.c`，以本节与下节为准。）

**执行流程核对（`HAL_TIM_PWM_Start(CH4)` 能否换成 `TIM_CCxChannelCmd`）**

结论：**在现有调用顺序下功能等价，但本次不改代码**。换法可行，然而收益仅是语义：
它把“计数器已启动”从 HAL 自管理降级为“`HAL_TIM_Base_Start_IT()` 必须先于 `CurrentSense_Init()`”的隐式契约。

启动顺序（`Core/Src/motor_control.c`，行号为该文件）：

| 位置 | 动作 | CEN | MOE | CC1E~CC3E | CC4E | PA11 EN | PB12 PWM_COTR |

| 44 | `DRV8353_Init()`（内含 `DRV8353_Enable()`） | 0 | 0 | 0 | 0 | **1** | 0 |
| 68 | `HAL_TIM_Base_Start_IT()` | **1** | 0 | 0 | 0 | 1 | 0 |
| 76 → `sense.c:44-45` | `CCR4=288` + `HAL_TIM_PWM_Start(CH4)` | 1 | **1** | 0 | **1** | 1 | 0 |

`HAL_TIM_PWM_Start` 实际做 4 件事（`stm32g4xx_hal_tim.c:1475-1516`）：① `ChannelState=BUSY`；
② `TIM_CCxChannelCmd(...ENABLE)` 置 CC4E；③ `__HAL_TIM_MOE_ENABLE`；④ `__HAL_TIM_ENABLE` 置 CEN。
而 `TIM_CCxChannelCmd` 只写 `CCER` 对应位（`8117-8132`），即只保留 ②。

逐项依赖：

- **CC4E**：唯一功能必需的位，换法仍保留 → 注入组触发链不变。
- **CEN**：第 68 行 `HAL_TIM_Base_Start_IT()` 内部已 `__HAL_TIM_ENABLE`（`474-509`），故第 45 行的 CEN 是冗余。
  副作用是：换法后若有人把 `CurrentSense_Init()` 挪到第 68 行之前，CC4 永不触发 → 卡在 `sense.c`
  “50ms 无数据”的 `Error_Handler()`（fail-fast，不会静默跑错）。
- **MOE**：不参与 `T1_CC4 → ADC 注入组` 的触发通路（MOE 只作用在最后一级输出使能）；此刻
  `CC1E~CC3E=0`，且 BDTR 的 `OSSR`/`OSSI` 均为 `DISABLE`（`Core/Src/tim.c:120-121`），MOE 由 1 变 0 时
  输出是“释放/高阻”而非被拉到 `OISx` 电平，引脚行为一致；第 79 行启用 CH1 时 MOE 必然被补上。
  旁证：故障路径 `Protect_StopPWM()`（`Core/Src/protect.c:37-49`）就是清 `CC1E~CC3E` + 清 MOE，
  但**保留 CEN 与 CC4E** —— 若 MOE=0 会掐断 CC4 触发，FAULT 态下 `InjMiss` 会暴涨，与实测不符。
- **HAL 通道状态**：换法后 CH4 的 `ChannelState` 停在 `READY`。全工程没有第二处对 CH4 调
  `PWM_Start/Stop`（已全仓搜索），本版本 `HAL_TIM_PWM_Stop`（`1531-1553`）也不检查通道状态，
  故当前无影响；但**永远不要对 CH4 调 `HAL_TIM_PWM_Stop`** —— 它会清 MOE 并 `__HAL_TIM_DISABLE`（清 CEN），
  采样与 FOC 节拍会一起停。调试量 `dbg.pwm_out`（`foc.c:1047-1053`）只读 CEN/MOE/CC1E~CC3E，不受影响。

### 2026-10-21 — 电流采样链路重构：ADC1 注入组 + TIM1_CH4 移相触发、换算系数修正

**背景**：ADC1 规则组由 4 通道改为 2 通道（CH4/CH8）后，`sense.c` 仍按 4 通道取数：
`adc_values[0/1]`（本应是 A/B 相电流）实际是 MOS 温度与母线分压，`adc_values[2/3]` 只是它们的旧副本；
A/B 相电流所在的注入组（CH2/CH3）从未启动、也从未读过 JDR。结果是电流恒在 0 附近，
母线/温度读数"看起来正常"但实际取错通道，电流环与过流/过温/母线保护全部失准。
另外 `ADC_TO_Sense = 4095×3.3`、`I_K = 1/(4095×3.3×20×0.001)` 乘除颠倒，
电流读数只有真实值的 9.18%（零点标定会吸收偏置，掩盖增益错误）。

1. 采样分工（方案 B）
   - `Core/Src/adc.c` / `Drive.ioc`：ADC1 注入组触发源 `T1_TRGO` → **`ADC_EXTERNALTRIGINJEC_T1_CC4`**；
     规则组保持 rank1=CH4(PA3, MOS 温度)、rank2=CH8(PC2, 母线)，DMA 长度 = 2 半字。
   - `Core/Src/sense.c`：新增 `adc1_values_reg[2]`（规则组/DMA，`[0]`=MOS 温度、`[1]`=母线）、
     `adc1_values_inj[2]`（注入组/中断读 JDR，`[0]`=A 相、`[1]`=B 相），ADC2 缓冲更名
     `adc2_values_ntc[1]`（NTC），删除 `adc_values[4]`。`CurrentSense_Update()` 改为
     `判 JEOS → 读 ADC1->JDR1/JDR2 → 算 A/B/C → 母线中值滤波读 adc1_values_reg[1]`；
     `TempSense_Update()` 改读 `adc1_values_reg[0]` / `adc2_values_ntc[0]`。`CurrentSense_Init()` 内完成

2. 采样时序（解决"电流采样落后于 FOC 更新"）

   - `Core/Src/uart_cmd.c`：`status` 与自动上报的 `ADC_A/ADC_B` 改读 `adc1_values_inj[]`，并新增 `InjMiss=` 计数。

### 2026-10-20 — FOC 20kHz 控制中断（ISR）复查：统一时间基准、nFAULT 快速停机、浮点算力优化

**背景**：对 TIM1 更新中断（20kHz / 50µs 一拍）做一次完整复查，关注三件事：

1. **一拍内的时间基准是否一致**——此前 ISR 里散落 8~10 次 `HAL_GetTick()`，跨毫秒边界时同一拍会拿到两个值，
   故障计时与状态机判定都在中断里，容易出现 ±1ms 的抖动与不可推理的边界。
2. **nFAULT（EXTI，优先级 0，高于 TIM1 的 1）的干扰关系**——原回调先做 2 次 `DRV8353_ReadReg`
   （各含 `DWT_DelayUs(100)` + 阻塞 SPI），约 **220µs 后**才执行第一条停机动作；期间压住 4~5 个控制周期，
   且会与主循环 `DRV8353_Recover()` 争用同一路 SPI2。
3. **一拍内的浮点算子**（`VDIV` / `VSQRT` / `fmodf` / CMSIS 三角）是否存在白算的部分。

本批只做"等效改写 + 时间基准统一"，**控制器参数、保护阈值、状态机行为均零变化**。

**改动**

**1. 中断时间基准统一为 `s_tick`**

- `Core/Src/motor_control.c`：新增 `uint32_t s_tick`；`HAL_TIM_PeriodElapsedCallback()` 的 TIM1 分支入口
  先 `s_tick = HAL_GetTick()`，**一拍只取一次**。
- `Core/Inc/motor_control.h`：`extern uint32_t s_tick;`。
- `Core/Src/foc.c`：ISR 侧全部计时改用 `s_tick`——开环转角度/悬停（`ol_move_t0` / `ol_pull_t0`）、
  对齐窗口（`align_step_time` / `align_accumulate`）、故障退避（`fault_recover_time`、稳定期判定）、
  `led_blink_tick`；`Core/Src/protect.c` 的编码器停转计时同步改用。
- **刻意的例外**：`FOC_Update()` 里"硬件恢复完成"处的 `foc.last_recover_tick = HAL_GetTick()`
  保留取"此刻"，因为它的用途是与 16s 稳定窗口比较，1ms 级差异无影响（已在代码注释中标明）。
  主循环侧（`FOC_FaultRecoverProcess()`、`DBG_Monitor_Update()`、`uart_cmd.c`）继续用 `HAL_GetTick()`。
- `foc.c` 的 `led_blink_tick` 加 `volatile`。

**2. nFAULT 故障路径重构（最快停机 + 状态可诊断）**

`Core/Src/main.c` `HAL_GPIO_EXTI_Callback()` 顺序改为：

```c
TIM1->CCER &= ~(TIM_CCER_CC1E | TIM_CCER_CC2E | TIM_CCER_CC3E);  // ① 立即封锁三相输出（约 10 个周期）
TIM1->BDTR &= ~TIM_BDTR_MOE;
if (hspi2.State == HAL_SPI_STATE_READY) {                        // ② 仅在 SPI 空闲时读
    fault_status1 = DRV8353_ReadReg(DRV8353_REG_STATUS1);         //    必须先读后关 EN
    fault_status2 = DRV8353_ReadReg(DRV8353_REG_STATUS2);         //    （EN 拉低会复位寄存器）
    fault_status_valid = 1;
} else {
    fault_status_valid = 0;                                      //    主循环 SPI 被占用，放弃本次读取
}
DRV8353_Disable();                                               // ③ 关栅极驱动
fault_code = FAULT_CODE_HARDWARE;                                // ④ 通知控制环
fault_triggered = 1;
```

- 新增 `volatile uint8_t fault_status_valid`（`main.c`）：为 0 时上报
  `FAULT: HW (STATUS unavailable: SPI busy at nFAULT)`，不再把上一次故障的 STATUS 位当作本次结果打印。
- `Core/Src/protect.c` `Protect_StopPWM()`：3 次 `HAL_TIM_PWM_Stop()` 改为直写 `TIM1->CCER` / `TIM1->BDTR`；
  同时删掉为抵消 `HAL_TIM_PWM_Stop` 副作用而补的 `__HAL_TIM_ENABLE(&htim1)`（CEN 由
  `HAL_TIM_Base_Start_IT()` 与 `HAL_TIM_PWM_Start()` 负责，计数器必须持续运行以维持 20kHz 中断与 ADC 触发）。
- `Core/Src/drv8353.c`：`DRV8353_ReadReg` / `DRV8353_WriteReg` 的 CS 建立延时
  `DWT_DelayUs(100)` → `DWT_DelayUs(1)`（单次寄存器访问省约 100µs，nFAULT 回调与上电自检同步受益）。

**3. `LED_Update()` 回归 20kHz 控制中断**

- `Core/Src/motor_control.c`：TIM1 分支恢复为 `if (motor_ready) { FOC_Update(); LED_Update(); }`。
- `Core/Src/main.c`：删除主循环末尾的 `LED_Update()` 调用（末尾只剩 `HAL_IWDG_Refresh()`）。
- `Core/Src/foc.c` `LED_Update()`：`now` 由 `HAL_GetTick()` 改为 `s_tick`，与故障分支的 `led_blink_tick` 同源。
- 原因：主循环的 `UART_Cmd_Process()`（串口 `ang=` 测试最长 ≈8s）与 `DRV8353_Recover()`（≈12ms）期间
  LED 会冻结、故障闪烁丢失；回归中断后任何情况下都能看见指示，代价约 0.5µs/拍（≈1% 的 50µs 预算）。

**4. 浮点算力优化（等效改写，结果不变）**

- `Core/Inc/sense.h`：新增 `I_K` / `I_B0` / `Vbus_K` 预计算常数。
- `Core/Src/sense.c`：`CurrentSense_Update()` 由"每相 2 次 `VDIV`"改为一次乘加
  `current_x = adc_values[i] * I_K - (I_B0 + offset)`；`bus_voltage` 改为 `med * Vbus_K`。
  `CurrentSense_Calculate()` 保留给上电 64 次零偏标定。
- `Core/Src/foc.c` `FOC_Clark()`：`/(1.73205f)` → `*0.57735027f`。
- `Core/Src/foc.c` 电压限幅/归一化重写：

  ```c
  float V_max   = vbus * 0.57735027f;      // Vdc/√3，无除法
  float inv_max = 1.0f / V_max;            // 全拍唯一一次 VDIV
  float vd_n = foc.Vd * inv_max, vq_n = foc.Vq * inv_max;
  float mag2 = vd_n * vd_n + vq_n * vq_n;  // 平方比较，常规路径不开方
  if (mag2 > 1.0f) { float k = 1.0f / sqrtf(mag2); vd_n *= k; vq_n *= k; foc.Vd *= k; foc.Vq *= k; }
  ```

### 2026-10-19 — `0x300` 新增「转动到位」主动上报事件（`0x09` 查询帧保持不变）

**背景**：`0x07` 开环转角度+悬停原来只能靠上位机周期发 `0x09` 轮询判到位——轮询慢会漏判/延迟，轮询快又占带宽。
新增事件驱动的「到位」上报；`0x09` 查询继续保留，用于查看回拉(PULL)等**任意时刻**的状态。

**改动**

1. `Core/Src/foc.c`：新增 `volatile uint8_t arrive_report_pending = 0;`；
   `FOC_OpenLoopMoveHold_Service()` 在 **RUN→HOLD（首次到位）** 时置 `1`。
2. `Core/Inc/foc.h`：`extern volatile uint8_t arrive_report_pending;`
3. `Core/Src/fdcan_app.c`：
   - `FDCAN_SendOLStatus(uint8_t evt)` 增加参数，写 `tx_data[7] = evt`；
   - `0x09` 查询改为 `FDCAN_SendOLStatus(0)`（查询响应）；
   - `FDCAN_App_Process()` 末尾消费标志并 `FDCAN_SendOLStatus(1)`（主循环上下文发送，不在中断里调 HAL）。
4. `Core/Inc/fdcan_app.h`：原型同步为 `void FDCAN_SendOLStatus(uint8_t evt);`。

**协议变化（向后兼容）**

`0x300 + NODE_ID` 帧的 **byte7** 由「保留 0」变为「触发来源」：

| byte7 | 含义 |
|---|---|
| `0` | `0x09` 查询响应 |
| `1` | 转动到位事件（自动上报，`byte0=2` 悬停保持） |

帧 ID、其余字节布局与含义**均不变**；旧上位机忽略 byte7 也能正常工作。

**行为说明**

- 只在**首次到位**上报一次；`PULL→HOLD`（回拉归位）不重复上报，避免电弹簧在死区边界抖动时刷帧；需要时随时 `0x09` 查询。
- 上报在主循环发出，正常延迟 ≤1ms；若主循环正被串口阻塞命令（`ang=`）占用，会顺延到命令结束。
- 主动上报**不刷新通讯心跳**（喂狗只在接收中断里），悬停期间仍须 ≥50 Hz 发帧，否则 20 ms 后 `COMM_TIMEOUT` 停机。
- TX FIFO 满时该帧丢弃，仅累加 `fdcan_tx_fail_count`（串口 `can` 可见），不自动重发。

**验证**：Keil 编译；上位机发 `0x07` 后**不轮询**，收到 `0x301`（`byte0=2, byte7=1`）即到位；再发 `0x09` 应回 `byte7=0`，确认查询通道正常。

**关联文件**：`Core/Src/foc.c`、`Core/Inc/foc.h`、`Core/Src/fdcan_app.c`、`Core/Inc/fdcan_app.h`。

### 2026-10-19 — LED 状态机整体移入 20kHz 控制中断（修饰阻塞期卡死与硬件错误闪烁失效）

**问题（改动前）**

1. `LED_Update()` 只在主循环调用，而主循环存在长时间阻塞：串口 `ang=` 测试命令（数百 ms ~ 数秒）、
   `FOC_FaultRecoverProcess()` 里的 `DRV8353_Recover()`（≈20ms）、`MotorControl_BootSequence()`。
   阻塞期间 LED 停在最后一拍的状态，故障也不会闪。
2. `MotorControl_BootErrorLed()` 每 200ms 只 `Run_Toggle()` 一次，而主循环每轮先执行 `LED_Update()`
   （IDLE → `Run_OFF()` 强制定灭）。结果翻转点亮后约 1ms 就被下一轮熄灭 → **实际亮 1ms / 灭 199ms，肉眼几乎不可见**。
3. LED 有 4 个写者（主循环 `LED_Update`、主循环 `BootErrorLed`、20kHz 中断里的故障 `Run_OFF` 与恢复 `Run_ON`），
   状态机跨两个上下文分裂，难以推理。

**改动**

1. **状态机整体移入 20kHz 控制中断**（`Core/Src/motor_control.c`）：
   `HAL_TIM_PeriodElapsedCallback()` 的 TIM1 分支改为 `if (motor_ready) { FOC_Update(); LED_Update(); }`。
   放在 `motor_ready` 之后，使**上电初始电平（`gpio.c` 写低 = 点亮）保持不变**，直到控制就绪才由状态机接管。
2. **`LED_Update()` 重写为三级优先级**（`Core/Src/foc.c`，每拍 50µs 刷新）：
   ```c
   if (MotorControl_BootIsHwError()) { 200ms 相位强制定亮/定灭; return; }   // 硬件错误慢闪 2.5Hz
   if (foc.mode == FOC_STATE_FAULT)  { 100ms 翻转一次; return; }            // 故障快闪 5Hz
   foc.mode == FOC_STATE_IDLE ? Run_OFF() : Run_ON();                       // 待机灭 / 其余常亮
   ```
   硬件错误分支**每拍都写**（按 `HAL_GetTick()/200` 相位），不会被其它分支覆盖，修复了"后写覆盖"失效的问题。
3. **新增只读接口** `MotorControl_BootIsHwError()`（`motor_control.c/.h`），供 `foc.c` 读取 `boot_hw_error`；
   删除 `MotorControl_BootErrorLed()`、`BOOT_DEV_ERR_BLINK_MS` 及主循环中的两处 LED 调用
   （`main.c` 的 `LED_Update()` / `MotorControl_BootErrorLed()`、启动序列里的两处 `LED_Update()`）。
4. **`Run_*` 宏统一**：只保留 `foc.h` 中的 `Run_ON / Run_OFF / Run_Toggle`，删除 `motor_control.h` 里的重复定义；
   新增 `LED_HW_ERROR_BLINK_MS = 200`。

**效果**

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 串口 `ang=` 阻塞数秒 | LED 冻结 | 20kHz 持续刷新，状态实时 |
| `DRV8353_Recover()` ≈20ms | 冻结 | 持续刷新 |
| 上电自检失败（硬件错误） | 亮 ≈1ms / 灭 199ms（几乎看不见） | **200ms 定亮 / 200ms 定灭（2.5Hz 慢闪）** |

### 2026-10-19 — 编码器改为单帧流水线读取，并彻底移除定时器中断刷新链路

**背景与约束**

- KTH7823 的 SPI **最高 SCLK 为 10MHz**，现有 9MHz（PCLK2 36MHz ÷ 4）已接近上限，**不能再靠提频**提速。
- 协议是**流水线**：当前帧发送命令，返回的是**上一命令帧的回读**；且 **CS 不允许连续拉低**，两帧之间必须有 **≥50ns 高电平**。
- 原方案为 TIM3 10kHz 中断刷新编码器（`KTH7823_UpdateISR`），额外占用一个定时器与一条中断，且打断了控制的时序一致性分析。

**改动**

1. **单帧流水线读取**（`Core/Src/kth7823.c`）
   ```c
   uint16_t KTH7823_ReadAngleRaw(void)
   {
       return spi_exchange_frame(0x0000);   // 发读命令，直接取回读（= 上一命令帧对应的角度）
   }
   ```
   - 旧实现"发 2 帧、丢第 1 帧、取第 2 帧"，现改为"每拍发 1 帧、直接用返回值"：连续发送同一读命令时，返回值始终是上一拍命令对应的角度，**语义等价，仅滞后一帧**（≈1.78µs）。
   - 线时 **3.56µs → 1.78µs**；CS 仍每帧"拉低→传输→拉高"，HAL 调用开销远大于 50ns，满足帧间高电平要求。
   - `KTH7823_Init()` 中保留一次读取，用于丢弃上电无效值并**建立流水线首拍**。
   - **未改** SPI 分频（仍 9MHz）、未改 `HAL_SPI_TransmitReceive`、未做寄存器级改造。
2. **移除定时器刷新链路（全工程无 TIM3）**
   - `Core/Src/main.c`：删除 `MX_TIM3_Init();` 调用。
   - `Core/Src/motor_control.c`：删除 `HAL_TIM_Base_Start_IT(&htim3);` 与 `HAL_TIM_PeriodElapsedCallback()` 中的 TIM3 分支；回调只剩 TIM1（20kHz 电流采样 + `FOC_Update`）。
   - `Core/Src/tim.c` / `Core/Inc/tim.h`：删除 `htim3` 句柄、`MX_TIM3_Init()`、`HAL_TIM_Base_MspInit/MspDeInit` 的 TIM3 分支（含 TIM3 时钟与 `TIM3_IRQn` 的 NVIC 配置）及其声明。
   - `Core/Src/stm32g4xx_it.c` / `Core/Inc/stm32g4xx_it.h`：删除 `extern htim3`、`TIM3_IRQHandler()` 与原型。
   - `Core/Src/kth7823.c` / `Core/Inc/kth7823.h`：删除 `KTH7823_UpdateISR()` 定义与声明。
3. **刷新路径唯一化**（`Core/Src/main.c`）
   主循环每轮**无条件**执行（`FDCAN_App_Process()` 之后、`HAL_IWDG_Refresh()` 之前）：
   ```c
   KTH7823_UpdateAngle();   // 单帧流水线读角度 -> 异常读数统计 -> 解包裹/野值剔除 -> 滤波 -> 多圈角
   KTH7823_UpdateSpeed();   // DWT 差分测速（一阶低通）
   DWT_DelayMs(1);          // 定 1ms 节拍（≈1kHz）
   ```
   不再有任何编译期开关，`KTH7823_UpdateAngle/UpdateSpeed` 全工程只有"主循环 + 串口阻塞测试函数"两类调用点，不存在并发刷新。
4. **阻塞式串口测试命令补刷新**（`Core/Src/uart_cmd.c`）
   串口 `ang=`（开环转角度/保持/回拉）在**主循环里阻塞**执行；原来依赖定时器中断刷新编码器，链路移除后必须自刷新，否则回拉判据拿到的是冻结角度。三个阻塞循环（运动 / 保持 / 回拉）内均已补 `KTH7823_UpdateAngle(); KTH7823_UpdateSpeed();`，节奏仍受 `DWT_DelayMs(1)` 约束。
5. **注释同步**：`protect.c`、`protect.h`、`dbg_monitor.h`、`kth7823.c` 中"编码器刷新由定时器中断完成"一类描述统一改为"主循环刷新"。

**效果**

| 项 | 旧（2 帧 + 定时器中断） | 新（1 帧 + 主循环） |
|---|---|---|
| 单次读取线时 | 3.56 µs | **1.78 µs** |
| 单次刷新总耗时（含 HAL / 滤波） | ≈10~13 µs | **≈6~8 µs** |
| 刷新率 | 10 kHz（TIM3 中断） | ≈**1 kHz**（`DWT_DelayMs(1)` 决定） |
| 20kHz 控制中断看到的角度年龄 | ≤100 µs | 最旧 ≈**1 ms** |
| 占用定时器 / 中断 | TIM3 + `TIM3_IRQn` | 无 |

- CPU 占用：1kHz 下编码器刷新总耗时约 6~8µs/ms，**不足 1%**。
- 角度滞后：返回值比旧实现多滞后一个命令帧（≈1.78µs），对 1kHz 刷新、保护判据均无实际影响。
- 保护逻辑未改：`Protect_EncoderStallCheck()` 仍按 `kth7823_raw_fault_cnt ≥ KTH7823_RAW_FAULT_LIMIT`（8 次无效读数）判失效，`encoder_update_count` 仍由 `KTH7823_UpdateAngle()` 递增。

**验证**

- 用 `arm-none-eabi-gcc -fsyntax-only`（`-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard -DSTM32G474xx -DUSE_HAL_DRIVER`）编译 `Core/Src` 全部源文件：**0 error**。
- 全工程检索确认已无 `TIM3` / `htim3` / `MX_TIM3_Init` / `KTH7823_UpdateISR` 引用。
- 仍需在 Keil 中完整编译、烧录验证；可用逻辑分析仪抽查 CS 帧间高电平 ≥50ns（HAL 结构下天然满足）。

**注意事项**

- **CubeMX**：`Drive.ioc` 中的 TIM3 配置（`Mcu.IP12=TIM3`、`NVIC.TIM3_IRQn`、`TIM3.*` 参数）需在 CubeMX 中**手动删除**，否则重新生成工程会把 TIM3 初始化代码加回来。
- 如需进一步提高刷新率，可后续单独评估（当前已不占定时器，只剩主循环调度抖动与滤波系数两项限制）；本轮按需求保持 1kHz 节拍、未改滤波系数。
- 首拍语义：上电后第一次 `KTH7823_UpdateAngle()` 拿到的是 `KTH7823_Init()` 那一帧命令对应的角度（有效，滞后一帧）。

> **注（2026-10-22）**：本条确立的「主循环 1kHz 刷新」方案已被同日「编码器刷新移入 TIM1 20kHz 中断」取代——
> 快路径（SPI 帧 + 解包裹）改在控制中断内逐拍执行，慢路径（滤波角度）仍留在主循环 1kHz。
> 因此本节中 `KTH7823_UpdateAngle/UpdateSpeed`、`KTH7823_RAW_FAULT_LIMIT=8` 等描述均为当时状态，以最新条目为准。

### 2026-10-16 — 故障掩码 `fault_mask`：一次故障事件记全所有触发保护 + 失联计时可观测

**问题**：`fault_code` 是单值、**后写覆盖**——同一拍内多个保护同时命中（如堵转 + 相电流峰值 + 通讯超时），
只有最后写入的那个能上报，上位机与串口日志看到的"故障原因"取决于巡检顺序，无法判断到底触发了哪些保护。

**改动：故障掩码**

- `foc.h`：新增 `FAULT_MASK_BIT(code)`（= `1u << code`，位 n ↔ `FAULT_CODE_n`，n=1..12）；
  新增 `extern volatile uint16_t fault_mask;`。
- `protect.c`：`Protect_StopPWM()` 入口统一汇总——切断输出前若 `fault_code != FAULT_CODE_NONE`
  则 `fault_mask |= FAULT_MASK_BIT(fault_code)`。全部 11 项保护分支与 nFAULT EXTI 回调都必经该入口，
  故掩码一次不漏。
- `main.c`：定义 `fault_mask`；主循环上报分支在 `UART_PrintFaultMask(fault_mask, fault_code)` 之后
  与 `fault_code` **同步清零**。
- `uart_cmd.c`：新增 `UART_PrintFaultMask()`，打印 `FAULT: code=u(name) mask=0xXXX {A|B|C}`
  （多位用 `|` 拼接，无位输出 `-`；掩码串用静态数组，主栈仅 1KB）。
- `dbg_monitor.h` / `foc.c`：`DBG_Monitor_t` 增加 `fault_mask`，`DBG_Monitor_Update()` 同步赋值，
  Keil Watch 中可直接查看本次事件触发过的全部保护。

**含义**：`fault_code` 仍是唯一故障源（决定退避与恢复逻辑，本批未改）；`fault_mask` 只是叠加的诊断信息，
在一次故障事件内累积、互不覆盖，事件结束（主循环上报）时与 `fault_code` 一起清零。

**同批：保护巡检顺序**：`Protect_FOC()` 中 `Protect_CommTimeoutCheck()` 由编码器检测之后提到**最前**，其余顺序未动。

**失联计时可观测（`comm_silent_ticks`）**

- `protect.c`：`comm_silent_ticks` 由 `static` 改为 `volatile` 全局（收到新帧即清零）；`protect.h` 补 `extern` 声明。
- ~~`uart_cmd.c`：`[EVT]` 行增加 `commSilent=<当前静默节拍>`；周期快照行增加
  `silent=<当前节拍>/<COMM_TIMEOUT_TICKS>`~~：这两处输出属于 `UartLog` 自动上报模块，已随该模块
  于 2026-10-20 整体删除；`comm_silent_ticks` 仍在 `Protect` 内部维护，可在 Keil Watch 中查看。

**调试（有意变更）**：`main.c` 主循环的 `DBG_Monitor_Update();` 当时处于**注释**状态
（Keil Watch 里的 `dbg` 会停留在最后一次刷新的值）；**现已于 2026-10-22 恢复为每轮调用**，见上方同日条目。
